# 创建为Daynight独立交付任务

把已经确定的交付拆分落实为真实 Daynight 任务。按已确认方案、拆分和目标仓库流程补全每项任务自身阶段的交付定义，登记并核对后返回，不重新开展需求、架构或实质拆分工作。

## 核对当前方案与创建范围

读取当前完整架构、评审结果和已确认的 breakdown，核对它们属于同一有效版本，并确认本次创建授权覆盖相应清单。有架构或方案生产任务时，读取完整任务并确认其实际 ID、所属关系和材料位置。沿用已有确认，不重复询问；代理评审通过本身不能代替项目要求的用户确认。

目标仓库明确的开发与 PR 流程、材料归属和已有例外优先于通用登记顺序，仍须遵守当前授权与产品约束。只登记当前阶段允许创建的实施、必要独立阶段交付与验收任务；不因本 skill 位于方案确认后就遗漏已经确认的仓库前置交付。已有任务自身已明确承担该交付并满足阶段要求时复用，不重复创建阶段。发现缺口时先核对已确认材料，补齐能够确定的登记内容。关键方案、任务边界或验收确需决定时，明确受影响项、具体问题、可选处理与建议，交回相应设计流程；继续完成不依赖该决定的准备。当前方案及阶段要求仍有效、定义与前置完整且创建授权明确的独立条目，可以继续登记；不能用部分登记绕过整体确认，也不自行改方案或新增工作。

每项任务应能从架构与共享材料中形成自己的：

- 目标与对整体要求的贡献。
- 自身阶段的范围、责任及留给其他任务的工作。
- 该阶段的选定方法、必要步骤和正式成果。
- 实际输入、来源、材料所有者及生产者与消费者约定。
- 成功、失败和重要边界的验收与完成条件。

实施任务另须明确代码责任、选定方案、必要详细设计和有序实施步骤；设计材料交付、独立审查或验收任务按自身成果定义，不强套代码实施栏目。验收任务登记前，按 [plan-actionable-verification](../plan-actionable-verification/SKILL.md) 核对候选版本、指定执行环境的能力、所需输入、前置责任和证据。将已明确的前置落实到任务定义与依赖；环境或权限仍未落实时，按上述流程明确缺口，不将该条目作为定义完整的交付任务登记。

不能只写“按照架构实现”，也不把全部架构复制到每个任务。内部调研、命令和代理分工留在 Session。

## 确认项目与已有工作

使用明确的 Project、设计所有者和 Goal 引用，核对实际资源类型与内容。参数及操作遵循当前 Daynight CLI 或 MCP 手册与 schema，不猜测资源 ID 或命令。

查找相同问题和交付范围的已有任务，包括必要历史，再读取完整定义、材料、状态和依赖。匹配的未完成工作可以按授权复用；已完成任务及成果只作为来源或前置，不追加新范围或重新派发。已有成果已满足当前要求时不制造重复任务；确有新的剩余工作时另建独立 Task，并说明与原成果的关系。不能只凭标题判断，也不接管活跃执行、重开终态或另建替代项绕过已有工作。

若当前授权需要更新既有任务，保留有效内容、责任和状态。复用 `proposed` 任务不自动接受它，只有明确的确认与状态变更授权才进入 `todo`。

## 整理状态、所属关系与材料

新建已确认的普通交付任务显式选择 `todo`，自动执行保持关闭。登记不设置 `in_progress` 或 `done`，也不启用 Worker。

涉及 Goal 时按 [dn-goal](../dn-goal/SKILL.md) 核对其实际身份、当前阶段、材料与成员规则，使用实际 Goal 作为 Parent；Parent 与执行前置分别核对。需要建立容器时先核对已有资源与创建授权，不因批量任务自动创建 Goal。

依据仓库流程和各任务实际输入建立前置。有适用架构或方案生产任务时，实施根通过普通 `dependsOn` 接在该生产任务及必需阶段交付之后，后继可以继承；去冗余后，每项实施任务仍须有全普通依赖路径追溯到生产任务。仓库要求设计材料先合并、独立审查等条件时，按其真实完成顺序设置前置。非实施阶段按自身条件建立依赖，不一律等待架构任务完成，也不能制造相互等待。Parent、材料引用或外部依赖不能替代必需的普通路径。例如 `架构 → 设计交付 → A → B` 中，后继继承已保留的普通前置。没有生产任务而仅有已确认材料时记录实际来源，不凭空创建依赖对象。

负责人和平台依据用户安排及实际实施、验证需求选择，不按当前机器或模型设置。其他字段遵循当前资源类型的约束。

共享需求、架构和整体验收保留在其实际所有者中，仓库材料遵守既有位置与生命周期。每项任务的 description 直接标明适用的生产任务 ID、共享材料所有者、必要来源路径、适用内容和已核对版本；实施任务及间接后继同样保留架构入口，并具备完整实施定义。任务、PR 与原生 Issue 的映射按实际范围和仓库关联规则记录，不强制一一对应；必要原生登记与收尾不能由 Daynight 记录替代。附件确需新增时，上传并读回后再加入真实引用。

## 批量登记与读回

1. 核对当前清单、任务边界、输入输出和必要依赖，建立生产任务、清单标识到实际资源 ID 的映射，明确预期的直接前置及普通、外部分类。
2. 按必要前置顺序创建或复用任务，保留每次返回的 ID，使用实际 Parent 和已核对的前置 ID。
3. 保存任务内容及必要材料。创建、附件、描述和关系更新分别核对，不能假定一起成功。
4. 更新使用决定所依据的准确版本，保留整数全部位数；冲突后重新判断，不盲目换成最新版本重放。
5. 完整读回各任务和必要来源，检查目标、范围、自身阶段的交付定义与完成条件、验收对象及环境准备责任、Parent、状态、责任、平台和权限。
6. 读回实际依赖图，与预期前置及分类比较，逐项验证所有适用的生产者和阶段前置，保留实施任务到已有架构生产任务的全普通路径，并检查去冗余后的路径完整性、阶段完成顺序与清单覆盖，确保没有遗漏、重复职责、无人承接的部署条件或错误前置。断开的分量分别核验；图读取失败或必要路径未验证时不能报告通过。共享材料引用不自动产生执行依赖。

部分成功时保留已有 ID 和映射，只恢复缺失操作。写入结果不确定时，结合原操作上下文、完整字段和资源身份核对，不能仅凭同名或一次空查询重复创建。

## 报告并结束

返回清单到实际任务的映射、创建或复用结果、真实引用、状态与 Parent、必要依赖、材料核对结论和具体缺口。

全部登记与验证完成后才报告交付任务已建立。登记成功不表示任务已启动、已通过派发复核或整体目标已交付，不自动派发、发送 Worker 指令或推进实施。

需要移交且当前请求或已有授权覆盖时，交由 [dn-handoff](../dn-handoff/SKILL.md) 核对指定任务并启用许可；登记本身不扩大该授权。
