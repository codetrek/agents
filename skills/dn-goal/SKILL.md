# 组织和维护 Daynight Goal

围绕一个整体目标建立清楚的工作归属、当前有效成果与完成依据。按当前请求和已有授权完成 Goal 的创建、组织或维护；本 skill 不自动开启持续驱动、Worker 执行、发布、合并或部署。

## 确认目标与实际资源

从用户目标、范围、约束和整体验收条件判断是否需要 Goal。多项需要共同验收的成果或仓库明确要求的阶段可以归入 Goal；单个独立小任务不强制建立容器。仅讨论或登记时完成该范围，不自动开始后续工作。

按当前 CLI 或 MCP 手册和 schema 核对 Project、账号及实际资源。先查找并读取相关候选及必要历史，再决定创建或复用；标题、旧的 `[Goal]` 标记和依赖图都不能证明它是 `type=goal`。创建结果不确定时核对原操作上下文与实际资源，不能凭同名或一次空查询重复创建。

新建 Goal 先保存当前已知目标、范围、约束和完成条件，通常使用 `todo`；不预填尚未形成的成果。空 Goal 合法，不为填充容器制造占位任务。创建、归属变化和材料保存分别读回，不能假定一起成功。

## 按仓库流程组织阶段与子任务

读取目标仓库根及适用目录的现有指示和开发、PR、材料、验收规范及已有例外，按指示优先级、实际授权和产品约束处理。仓库要求的阶段、正式成果、确认点、材料生命周期和交付条件优先于通用组织建议；复用覆盖当前范围的已接受成果，不统一规定文件名或需求、架构、实施的固定流水线。

Goal 的普通直接子任务通过 Parent 表达所属关系；依赖表达真实前置，材料引用表达来源，三者分别核对。Goal 不嵌套，也不是依赖图节点或 Worker 执行对象。成员清单按实际 Parent 遍历所有页面；整体核对包含已结束的子任务，操作只针对当前请求选定的范围。失败读取不能当作空集合，跨 Goal 或无 Parent 的依赖不会自动成为成员。

每项子任务有自身目标、范围、责任、输入、成果与完成条件，并能说明对整体要求的贡献。仓库要求独立承接、交付或验收的正式阶段可以建 Task；文档、commit、命令、调研轮次或代理分工本身不构成拆分依据。核对完整目标、必要阶段、集成、消费者采用和整体验收均有承接，按实际前置安排安全顺序。

代码目标的整体及子任务验收按 [验收对象与环境](../plan-reviewable-changes/SKILL.md#代码验收的对象与环境) 针对指定提交和受控实例完成。待发布、待线上部署或待用户升级不自动成为代码任务的完成条件；明确要求的运维交付按其自身范围、责任和真实依赖管理。

每项 Task 按自身原定范围验收；实际成果、必需验证和约定交付及收尾条件满足后，立即按其执行合同提交完成并读回，不能因整个 Goal 尚未结束而留作持续追加工作的容器。Worker 报告完成不代替实际验收；原范围内的完成条件仍未满足时，继续处理该范围的问题，不为提前关闭而拆走必需工作。

原 Task 完成后发现的新需求、后续改进、独立验收或修复，另建有独立身份、范围和完成条件的 Task；已有匹配的未完成后续任务时复用该项。保留与原成果的来源关系，实际需要时建立依赖，再按授权移交。不向已完成 Task 追加执行指令、改写范围或自动重开；即使状态尚未同步、旧 Worker 或 Session 仍可联系，也只核对原任务的验收与完成提交。实际取消或恢复仍依用户的明确管理指示处理。

仅按当前阶段允许的范围和创建授权登记；未确认方案不提前转成已确定实施任务。必要后继的登记若属于当前阶段完成条件，应登记并读回后再结束该阶段，登记不启动其执行。复用 `proposed` 不自动接受它；组织 Goal 不授权接管、重分配、重开子任务或改变已有执行。

Task、PR 和仓库原生 Issue 的对应关系按实际成果与仓库规则确定，不强制一一对应。原生关联、责任、父子关系和适用收尾仍须维护与核验；单个 Task 完成不能关闭范围更大的 Issue，共享 Issue 仍开放也不自动阻止已满足自身条件的 Task 完成。

## 保存共享成果与整体进展

Goal 保存当前有效的整体 spec、架构、任务拆分、关键决策、阶段成果、交付与整体验收结论，以及已达成结果、剩余范围和重要阻碍。无论由当前会话还是子任务讨论、调研、设计或拆分产出，形成有效整体结论后都更新 Goal 并读回，不能只留在子任务、聊天或 Thread。

详细材料保留单一有效所有者，遵守仓库规定的位置、版本和生命周期；Goal 的当前材料应能独立说明整体结论并准确定位详细来源，不复制出相互冲突的定义。已接受且不可变的资料按仓库规则建立后续记录，Goal 同步有效变化及真实引用。总体讨论归 Goal Thread，采纳的决定仍须进入有效材料。

子任务保留自己的定义、责任、状态、结果和证据，直接标明必要的 Goal 与共享来源入口。生产任务和材料拥有者可能不同，按实际身份和路径引用，附件另行读取；Task 版本不冻结附件或其他资源。

在有效范围或决策变化、阶段结果形成、交付与验收发生或重要阻碍明确时更新整体材料与进展。服务的 `progress` 是子任务数量统计，不自动同步结论，也不能证明目标完成。执行安排、工具活动、原始日志、操作授权与恢复上下文留在 Session。

## 主动维护 Goal 状态

读取当前真实状态，按实际工作和项目流程维护 Goal；状态语义与写入方式以当前产品手册为准，不从数量进度推导完成。

| 实际情况 | 状态维护 |
|---|---|
| 仅登记、尚未实际开始 | 保持 `todo`，读取或登记不表示开始 |
| 已开始或接续已授权的整体工作 | 核对已进入 `in_progress`，必要时更新并读回；子 Task 实际进入 `in_progress` 可按当前产品规则自动启动 `todo` Parent，先读回避免重复写入 |
| 已开始但等待 CI、审查、用户决定，或暂时受阻、暂停驱动 | 保留真实未完成的 `in_progress`，记录必要说明，不以完成、取消或退回 `todo` 代替等待；不虚构 `blocked` 或 `paused` |
| 完整目标已交付且整体验收通过 | 保存并读回结论，核对必要子任务的完成合同，再更新为 `done` 并读回 |
| 用户明确取消或恢复已结束的 Goal | 核对具体意图与授权后按产品规则操作；取消不证明交付，不因新发现剩余工作就自动重开 |

已有 `in_progress` 不重复写入或重启状态区间。Goal 的取消与恢复不同于普通 Task 的不可逆取消；暂停或停用驱动不自动取消 Goal。结束 Goal 会影响后续自动领取，但不代表子任务或已有 Worker 已取消、停止或完成，分别核对其真实状态与管理权限。

每次状态或关系写入使用该资源决策所依据的准确版本，冲突后重新判断；响应丢失先核对实际结果，不盲目重放。Goal 负责人不自动取得变更其他账号任务或控制已有执行的权限。

## 核验整体完成与返回

按当前确认的完整要求、仓库完成标准、实际组合成果、适用 PR 合并和原生工作项收尾核验整体验收。PR 就绪、Task 完成、Issue 关闭和 Goal 验收分别判断；后续验收不自动成为所有 PR 的新合并门槛，规定的合并前验证仍须满足。

全部子任务终态、进度满额、空就绪列表或已有 `done` 状态均不能替代验收；取消的子任务和不可读产物不能抵充必需成果。发现遗漏或未验证要求时继续完成已授权的核对与准备，实质范围变化或确需外部条件时提出具体问题与建议，不虚构完成或额外目标。

返回实际 Goal、相关任务与材料引用、整体结论、状态、已完成操作及具体缺口。仅组织或登记的请求到其约定结果即返回，不因读取本 skill 自动派发或持续调度；持续驱动沿用已明确激活的上层流程。
