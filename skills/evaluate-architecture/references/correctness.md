# 正确性与故障边界

先问调用者可以把哪件事当成事实。例如「收到确认后写入不会丢失」「同一请求最多扣款一次」「索引允许滞后，但必须在约定时限内追平」。前两种约束一旦被打破，事后补救不能使它们重新成立；最后一种允许中间状态，评价时须核对偏离范围、恢复责任、期限和最终结果。

## 怎样取证

1. 选一个后果重大的承诺，写出它在什么输入、初始状态和故障条件下成立。纯计算选能改变结果的分界点，核对分界两侧、等于边界时的结果及算法不变量；有状态操作选一次接受、一次应拒绝的转换，以及最容易把已生效误认成未生效的位置。
2. 为选中的操作列一条时间线：`事件 → 已持久化的事实 → 已发生的外部效果 → 调用者知道什么`。分别标出提交、答复和重试的位置。在可能中断处停下，沿实际处理路径继续查：谁能重新发起、依据什么判定结果、同一操作再次执行会怎样？并发时围绕共享状态排出允许出现的交错。区分「请求已发出」「本地记录成功」「对方已生效」，为结论所依赖的事件附上实现、契约或同一请求的记录。
3. 从受保护的数据或副作用反查其他写入者，如后台补偿、批量导入。模块级可以把有据可查的上游前提写成条件；系统级要核对每个实际调用者是否满足它，以及跨组件的空档由谁负责。一个组件的事务只证明事务内的事。

## 怎样定档

- **强：** 关键承诺已经核实，还能指出设计带来的具体优势。例如所有写入路径都受同一原子约束，新增写入者也无须各自实现易遗漏的并发判断。仅证明确认后的写入能经受约定的中断，说明持久性达标；证据充分本身不加档。
- **足够：** 支持范围内的成功、拒绝及适用的中断有可信语义；失败的影响、调用方可采取的行动和恢复结果都符合约定。
- **有短板或隐患：** 关键约束成立，但某个次要结果已出现偏差，或具体条件会削弱余量。区分已发生的影响与有依据的风险，例如实际积压增长正让恢复耗时逼近期限。
- **不足：** 在承诺支持的条件下已有反例违反关键约束，或实现及有效契约足以推出这个反例。限定受影响的操作；其他路径成功不能抵消它。

只看到超时，或只看到可能的重复发送，两者都不能证明重复生效。若接收方行为可能改变档位，保留已知事实并标为**证据不足**。无持久化的纯函数可以将崩溃恢复列为**不适用**，但仍要评价计算结果。

## 假设案例：扣款后的答复丢失

支付服务承诺同一受理请求最多扣款一次。对请求 R，本地日志显示首次等待超时，恢复任务随后重发；重发沿用了 R。到这里可以确认重复发送，整条扣款链仍是**证据不足**。接着核对支付方账本：两条独立、已入账的扣款都归到 R，第二条随后退款。净额恢复了，但第二次入账时承诺已经失守，该服务在「答复丢失后重试」场景判为**不足**。若评估的是改动后的版本，应核对支付方对同一键的处理契约，并在同一中断场景核对两次调用只产生一笔扣款；其他支持的写入入口也守住约束后，才能上调服务的档位。
