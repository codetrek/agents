# 依赖与契约

**要判定什么：** 调用者只凭双方承诺的行为，能否在每种重要结果出现时做对下一步？依赖可以表现为函数签名、消息、文件格式或启动顺序。公开约定可以由类型、文档或有意保障外部行为的测试表达；有接口名称或编译通过，不能说明双方理解一致。

## 从调用者的选择倒推契约

1. 选一个实际受支持的调用者和一个它必须作出的选择，例如「查不到时创建，暂时读不到时保留原状」。模块级从使用该接口的函数和公开导出查起；仓库级选择实际交换数据的一对制品，核对部署配置和受支持的版本组合。优先选猜错就会影响数据或用户结果的选择。
2. 并排写下「产生方在什么条件下给出什么」「调用者能从中看见什么」「它应当怎样做」，至少覆盖能让调用者采取不同动作的结果。仅在场景需要时补充单位、缺省值、排序、重试、游标或资源释放等条件。对照签名、序列化和错误转换处，以及调用者解码后的实际分支，避免把底层可见的信息当成对外承诺。
3. 区分契约与偶然事实。若调用者读取内部字段、匹配可翻译文本或依赖注册顺序，核实这些细节是否被公开且受支持。构造一个仍遵守约定的生产者变化，推演调用者是否仍会选对分支。反过来，若怀疑信息丢失，查包装层是否另有公开状态码、结果类型或元数据可区分；同时核对调用者拿到的版本确实包含它。
4. 用实际调用测试、协议样例或历史替换交叉核对两个端点。记录改变结论所需的证据：例如只有在公开契约保证稳定排序时，调用者取首项才可靠。仓库内只找到生产者时，可以评价其声明，消费者是否正确使用要单独限定。

## 如何定档

- **强：** 实现替换、内部调整或独立调用者接入等证据显示，只依靠公开契约仍能正确区分关键结果并处理失败。
- **足够：** 对当前调用者，必要的输入、结果、错误和调用顺序有明确约定，沿实际路径能据此完成所需操作。
- **有短板或隐患：** 当前动作正确，但调用者确实依赖未承诺的细节；说明哪种被允许的变动将改变其行为，或已有何种局部影响。
- **不足：** 两端已对同一结果作出冲突解释，或接口丢失了调用者作出关键选择必需的信息，导致当前承诺无法保证。

缺少可能改变判断的消费者实现、版本或真实协议样本时，标为**证据不足**并写明缺口。没有网络接口不意味着契约**不适用**；若被评对象确实没有独立版本的调用者，独立升级这一项可不适用，仍判定进程内调用契约。

## 假设案例：读取草稿快照

编辑器必须在无快照时新建草稿，在存储故障时保留原稿并提示重试。存储服务明确区分 `404` 和 `503`；看服务协议似乎已经足够。但被评对象是编辑器使用的快照模块：适配器的 `load(id)` 将这两种响应都转成 `undefined`，编辑器收到它就创建空白草稿。核对调用点和故障用例，`503` 只写入内部日志，调用者的返回值和异常通道都没有保留区别，故障用例实际打开了空白草稿。

该模块面向此编辑器的契约评**不足**：调用者无法选择要求的重试动作。证据足以说明错误界面，尚不能断言原稿已被覆盖；要判断数据影响，继续核对空白草稿的首次保存条件。重新评价契约时，用编辑器实际支持的模块版本核实两种结果能否区分，以及编辑器是否分别选对动作。
