# 安全性

从需要保护的资产或能力出发，写一句可以核查的要求：谁可以对哪个资源做什么，或谁提供的输入最多可以消耗哪种资源。没有账号系统的公共解析器也有信任边界：文件来自调用方，解码消耗宿主的资源。判断依据是对象承诺的用途、实际输入来源、授权主体和失守的后果。

## 怎样取证

1. 选择越过信任边界的代表性操作。对租户数据，可选同一资源归属下的允许读取和另一归属下的拒绝读取；对文件处理，可选约定上限内、刚好达到上限和超过上限的普通样本。先说明预期：拒绝是否应无副作用、哪类信息不能进入结果或日志、要限制的是已解码大小还是传入字节数。按相关性选择，避免套用与资产无关的检查。
2. 从入口追到最后能阻止效果发生的位置。记下 `输入或主体 → 身份或资源归属的可信来源 → 执行约束的位置 → 允许与拒绝的结果`，附上实现和已有验证记录。确认校验所针对的资源就是最终读取或更改的资源；对于资源上限，则确认受限的计量单位以及限制何时生效。客户端筛选、接口声明和配置示例各自只能说明流程的一部分。
3. 从同一资产反查其他输入方式：导出、后台任务或另一个公开构造函数是否也经过相同约束？找有不同来源或责任方的入口比重复核对同一路径更有辨别力。模块报告写明宿主必须履行的前提；部署报告另核实际生效的身份、配置和边界。把尚未取得的材料与已有证据明确分开。

## 怎样定档

- **强：** 主要边界上的保护都已核实，且有证据表明它不易因入口变化失效，例如唯一的资源访问点强制绑定可信归属，所有公开路径的允许与拒绝都可追溯。一个简单的共同约束可以有这种优势。
- **足够：** 在声明的信任条件和使用方式下，已核实的控制足以保护相关资源，拒绝行为及副作用符合约定。
- **有短板或隐患：** 关键保护仍成立，但已有局部偏差或具体的失守条件，例如即将改变的归属规则由两处独立实现，且已有两处改动不同步的记录。指出影响和触发条件。
- **不足：** 有证据表明受支持的操作已允许越权访问、泄露受保护信息或破坏关键资源约束。受影响的用途不能靠其他路径的防护抵消。

源码里的保护已证实、关键部署条件尚未核实时，可以肯定模块保证，部署层记**证据不足**。宿主的账号管理可能对独立解析库**不适用**；只有能说明对象无相应资产、信任转换或受托控制时，才排除相应事项。

## 假设案例：上传文件的大小上限

某解析库要求「传给解码器的原始输入不得超过上限」。字节数组入口先核对长度；流入口有界读取；两者都通过唯一执行长度校验的入口进入解码器。已有边界用例显示两种入口在上限处正常解码，超过上限时均返回拒绝，解码器没有被调用。这些证据支持该库在这项保护上为**强**，并未证明解码后的内存占用有界。若评估整套上传服务，另有「接收端不得完整缓存超限文件」的要求：只见到代理配置示例时，部署结论为**证据不足**。下一步核对目标版本实际生效的接收配置与缓冲记录；若记录显示接收端完整缓存后才交给库拒绝，服务在这项关键要求上就是**不足**，库的结论仍成立。
