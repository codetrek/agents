# 职责与边界

**要判定什么：** 对一条规则、一个状态或一项决定，谁有权让结果生效？例如「封账后不能再记账」涉及提示用户、判断账期和写入分录三件事。三者分工可以很清楚；真正需要解释的是，提示过期或入口意见不同时，哪个决定约束最终账本。

## 从规则追到生效处

1. 选择失守后会改变调用者结果的一条规则，写明它约束的实体、动作和生效时刻。优先选择有不同入口或近期改过的规则，更容易分辨职责是由结构保证，还是靠几处实现恰好一致。对纯计算模块，可以选「谁确定舍入方式」这样的决定，不必虚设持久化层。
2. 从日常入口顺查，分别记下谁提供事实、谁解释规则、谁能拒绝、谁能让状态生效。例如按 `导入命令 → 暂存 → 入账 → 余额查询` 追踪，直到能说明哪一步以后余额会变化。缓存、投影、预校验可能重复计算；先核对用途与权威数据，别把每个赋值都算作第二个所有者。
3. 从生效处反查。仓库级可从表的写权限、更新语句、事件发布点追到批处理、管理操作及其他服务；模块级从可写字段、构造函数和导出方法追到调用者。检查能独立提交结果的路径，或用封装、权限等证明其必经同一决定点。若只有一个入口，查明它怎样封装决定即可。
4. 找一个会区分两种解释的场景：用同一实体、同一状态和同一动作比较两个入口；若声称规则分散，检查底层是否还会统一拒绝；若声称归属唯一，检查后台任务能否直接写。多个组件共同完成事务本身没有问题，关键是能否说清各自对哪项结果负责。

## 如何定档

- **强：** 路径和限制能说明最终决定归谁；真实变更或可验证的封装表明，其他入口无须各自维护同一条权威规则。
- **足够：** 在代表性流程中，规则、权威数据和协作职责都有明确归属，当前约定有相应执行点。
- **有短板或隐患：** 关键结果仍成立，但存在独立维护同一判断的路径；给出已经发生的维护偏差，或指出已知规则变化怎样使某一入口漏改、谁会受影响。
- **不足：** 必需的决定无人负责，或不同路径能让互斥的结果生效，关键约定已失守。

已知有另一条写入路径，却拿不到它的实现或权限配置，而它可能绕开检查，整体标为**证据不足**；保留对已查入口的结论。模块只读时可把「谁写上游数据」列为**不适用**，仍评价模块自己承担的筛选、呈现或转换职责。

## 假设案例：封账后的批量导入

评价账本仓库能否保证「封账后不再增加分录」。网页和导入程序都检查账期，看上去各有决定权。反查余额查询发现它只读 `ledger_entries`；导入程序写的是 `import_rows`，即使暂存成功也不计入余额。两种入口最终都调用 `post_entries`，该过程在提交分录的事务内锁定账期并检查状态；部署角色的授权清单显示它们只能调用该过程。一次先暂存、再封账、后提交的集成测试也确认余额未变。

对本仓库部署的这两种入账入口，可评**强**：撤掉入口预检也不会放行已封账分录，维护者只需在入账过程维护最终规则。若要把判断扩大到仓库外的财务修账工具，先取得其数据库角色和实际写入路径；凭现有测试不能推断它也受同一限制。
