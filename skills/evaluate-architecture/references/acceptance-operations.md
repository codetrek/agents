# 验收与运维

评价的是一项已经实现的能力：交付方能否证明指定版本的行为符合要求，运行方遇到问题时能否决定该怎么处理，并确认处理结果。测试是否容易编写属于可测试性；故障有没有破坏不变量属于正确性。这里关心的是**谁凭什么证据知道正在运行哪个版本、发生了什么、下一步做什么**。

## 选一条交付路径和一个处置决定

从仓库实际交付的制品开始，如库包、命令行工具或服务镜像。选一次有代表性的升级或验收，明确评估到哪里为止：库作者可能只负责可识别的包版本和对外错误，服务团队则可能负责发布、监控和恢复。用项目自己的验收和恢复承诺作基准；没有承诺的响应时限就不自设分钟数。

从一个真实故障，或一项确有影响的故障假设中挑出**需要区分的两个状态**。例如后台作业「仍在正常排队」与「执行失败等待干预」都可能表现为请求尚未完成，但要求的处置相反。记录谁要区分它们、允许查看什么信号，以及误判的后果。这样比清点有多少日志或监控面板更有判断力。

## 沿证据链走两遍

1. **从制品到验收结果。** 找构建或发布记录、制品标识和实际启动入口，核对验收结果是否绑定同一候选版本与关键配置。再从结果逆推一次：能否重建被验证的版本和测试数据？生产环境当前正常，并不能证明下一次发布的候选正确。
2. **从症状到下一步操作。** 假定没有作者在场，按值班者或宿主当前可用的文档、错误结果和运行信号判断上述两种状态。记下第一个能区分它们的证据，以及能据此采取的动作。一个故障码只有在责任方能据此决定重试、等待或升级处理时才有用。
3. **从处置到可核实的结果。** 找一次演练、受控验收或事故记录，看恢复后怎样核对服务和数据。进程恢复健康不一定表示积压已消化；需要核对到哪一步取决于原承诺。只读评估可沿记录推演，将推演与实测分开，无需操作生产系统。
4. **回查证据缺口的归属。** 评估者打不开日志，但值班者可以提供关联到版本的诊断记录，这是访问限制。若已有证据表明连获授权的责任方都拿不到所需信号，才是系统能力缺口。先问“出示哪一份记录能改变结论”，再决定补取证还是建议改架构。

最小记录可以是一行：`候选版本 → 验收入口及结果 → 运行症状 → 区分状态的信号 → 责任人处置 → 恢复判据`。某一环由宿主承担，写明交付给宿主的版本、错误或状态契约即可。

## 如何定档

- **强：** 在对象负责的范围内，代表性证据显示能稳定完成整个判断链，且有可说明的优势。例如非作者依据包版本及公开错误就定位了故障；或服务在恢复演练中能区分过程状态，确认对用户的影响已消除。
- **足够：** 有权限的执行者可以验收指定版本；重要故障能定位到可采取行动的程度。对象承担恢复时，有符合承诺的处置与结果核对路径。
- **有短板或隐患：** 当前关键要求仍满足，但有具体现实代价或风险。例如处置记录显示一项常见故障只能由一名维护者解释，轮值切换会延长诊断。说明已发生的影响或触发条件。
- **不足：** 已确认必要的验收或运行决定无法可靠做出，例如系统验收的制品与要交付的制品无法对应；或已发生关键故障，但负责恢复的人无法获知必要状态，也无等效核对手段。

缺少决定性记录时是**证据不足**。库不负责宿主的部署恢复，这部分是**不适用**；库自身若需要交付给调用方，其版本识别与错误契约仍需评价。

## 判例：服务恢复了，积压恢复了吗？

假设项目承诺重启后能继续消费已接受的作业，并让值班者确认积压已处理。候选镜像摘要与验收报告一致；演练记录显示工作进程重启且健康探针返回正常。这些证据支持“验证了正确版本”和“进程已恢复”，还不能判断队列已清空。若评估者只拿到健康探针截图，**恢复结果待核**：请责任方提供队列水位、作业状态读回或其他等效证据。若演练已证实仍有未完成的作业，而值班者依照现有信号宣布恢复，且服务没有其他核对方式，则对该恢复承诺判**不足**。同一现象不能据此推导“作业丢失”；作业是否丢失要沿写入和消费语义另行取证。
