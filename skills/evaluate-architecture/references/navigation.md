# 代码组织与可导航性

**要判定什么：** 给一个熟悉业务但不记得文件位置的维护者一项真实需求，他能否沿代码中的线索找到会生效的实现、规则和验证位置？分层与按功能分组都可以成立；要检验的是目录、命名、导出和装配能否共同解释「为什么改这里」。

## 走一遍维护者的定位过程

1. 从常见维护请求选样，例如「修改 CSV 导出的日期格式」。优先用近期真实变更：先只看需求原文和当时的代码，保留变更差异作为事后对照。若没有历史，就从公开命令、界面用语或库接口起步，明确这是一次定位推演。涉及多个支持平台时，挑会改变实现选择的平台核对。
2. 从该起点追到实际入口、注册或构建配置、生效的实现及验证用户结果的测试。每逢同名候选，记下哪个线索能排除另一份：例如发布包的导出、构建标签、命令绑定或插件注册。对模块可从它导出的符号向内追；对仓库，先从发布制品追到正确的包。搜索命中只是候选，命中最多的文件未必运行。
3. 列出据此预计要改和验证的位置，再看真实变更、构建目标或同级功能。多出来的文件分别是什么：自动生成的副本、可独立维护的实现，还是另一个也会读取该结果的入口？检查入口附近的线索或可检查的约定能否解释它。最好从测试反查一次，确认它实际组装的实现与交付给用户的一致。
4. 想推翻「这里很难找」，先尝试项目正常提供的导航方式；明确的注册表就能解释必要的跨目录跳转。想推翻「很好找」，沿另一条受支持入口或构建条件重复定位。文件数、行数和跳转数只指出值得查看的位置；一个完整表达规则的长文件可能比多个只转发的小文件容易维护。细看粒度时可参照 [code-structure](../../code-structure/SKILL.md)。

## 如何定档

- **强：** 维护者从稳定的入口就能判定哪个实现生效、去哪里验证改动，省去对多个候选逐一排查的成本。真实变更、多个入口的对照，或单入口模块的导出、构建关系与契约用例，都可证明这种优势；无需等待第二个入口或变更历史。
- **足够：** 按仓库的常规搜索和调用关系能找到并解释生效实现和验证位置，必要的跳转有可追溯的原因。
- **有短板或隐患：** 常见改动存在貌似同等权威的落点，或需靠未体现在组织方式中的背景知识才能找全；指出哪个目标可能漏改，或已经造成什么局部返工。
- **不足：** 组织上的歧义已妨碍必需的维护工作，有证据显示发布漏改、误改了不生效的实现等后果，并能联系到让维护者走错的线索。

缺少决定实际入口的装配清单且不同选择可能改变档位，标为**证据不足**，不要把「还没找到」当作难以导航的证据。单一库没有多平台装配时，这一分支**不适用**；常规维护者能否找到规则和测试仍然适用。

## 假设案例：下载与邮件共用的报表

需求要求网页下载和定时邮件中的销售 CSV 使用同一日期格式。从下载路由可追到 `sales/csv`，其测试也断言了日期样例。维护者据此改了格式；对应版本的发布回归记录却显示邮件仍是旧格式。反查邮件附件，调度清单用编号 `R17` 选择 `jobs/r17/render`；该标识在销售模块和测试中都没有引用。再核对实际交付包，确认编号映射仍启用，可排除这只是历史脚本。下载测试只装配网页处理器。

对该仓库「修改销售报表两种交付渠道」这一维护场景评**不足**：命名和装配掩盖了第二个落点，已导致一次可核实的发布漏改。单独评价 `sales/csv` 模块则不能把仓库的装配问题算在它头上；若要推广到其他报表，下一步从另一项真实报表需求检查编号映射是否造成同样的定位问题。
