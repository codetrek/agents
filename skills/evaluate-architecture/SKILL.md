# 评价现有架构

评价实际代码如何服务当前目标、应对可预见变化和处理失败。适用于仓库、系统或模块的现状评估；评审待实施的设计方案使用 [my-design-review](../my-design-review/SKILL.md)。评估本身不授权修改代码或登记外部任务。

## 建立评价基准

说明评价对象、版本和范围，确认它承担的能力、主要调用者、关键约束与不可接受的结果。区分对象自身的责任与对外部环境的假设。

## 从全貌到关键路径，再回到整体

1. **先看全貌，暂不定档。** 评仓库，从真实入口、构建与部署关系认出主要组件及外部系统，沿一条主流程说明控制和数据怎样流动。评模块，从公开契约、真实调用者和直接依赖开始。用几句话或一张简图讲清谁负责哪一步，并标出尚待验证的判断。
2. **选可能改变结论的路径。** 选有代表性的常见操作、可能发生的变更和后果严重的失败。对每个场景写出要验证的判断，以及什么事实会推翻它；优先查关系到关键约束、存在多个独立入口或证据相互矛盾的地方。
3. **沿路径逐层核实。** 从组件间的约定追到负责的模块，必要时再查函数、数据约束、配置、测试或运行记录。也从最终写入或外部效果反查其他入口。证据已能区分相邻档位、剩余未知不会改变结论时，就停止这条路径的下钻；若关键证据不可得，则缩小结论范围或标为证据不足。
4. **回到声明的用途。** 区分单个实现、模块契约和跨组件组合的结论。组合行为需要交接处的证据，例如发送方承诺的结果是否足以让接收方做对下一步。十个维度是观察角度，无须每层重复打分；整体评价按组合后的实际行为定档，不能取模块分数的平均值。多个维度指向同一根因时，汇总说明它的不同影响。

例如评价「已取消的订单不得再发货」：先找出 API 和后台补发两个入口，再从实际发货处反查，核对并发取消时最终生效的状态约束。若两条路径都必经同一处原子检查，就集中验证该处；若只查到 API 的预检，就只能评价 API 的预检。若证实后台能够发出已取消订单，一条反例便足以否定这个系统承诺。

## 分工与维度报告

主评先确定对象、版本、声明用途和关键路径，再把同一份背景和取证范围交给各维度的评审者。使用 subagent 时，每个适用维度由一位主责评审者按对应指南独立判断，交回可独立阅读的维度报告。并发受限时可以分批审；同一人承担多个维度时仍分别给出结论。评估小模块时，各维度报告可以是同一文档中的独立章节。不适用的维度由主评说明原因。

每份报告先给出**本维度的判断**：覆盖哪些场景、评为什么档、决定档位的证据、值得保留的设计，以及哪些路径尚未核实。随后列出本维度的 **Top N 问题**：按对声明用途的影响优先排序，再考虑波及范围及触发条件。每条给出编号、具体结论及其置信度、版本和证据位置、已发生的后果或有依据的风险，以及优先采取的行动。

**同类问题反复出现时，先归类再排序。** 用具体的共同模式命名，例如「调用者依赖错误提示文本分支」。若后果和处置可以一起说明，用一个问题编号，只占一个 Top N 名额；注明「已核实 3 处」，逐一列出对应版本的 `路径:行号`、符号或运行入口，并标明各处特有的影响。位置多时可在报告末尾列全，正文引用该清单。同类不等于同一根因；若根因、关键后果或处置不同，可放在同一类下，但分别编号、定优先级。未经核实的搜索命中不计入出现数。

**N 只限制单个维度向用户展示的问题数。** 用户指定的维度上限优先于通用上限；未指定时，主评按范围和评估目的确定。例如「各维度 Top 20，安全性 Top 50」表示安全性最多列 50 条，其余各列至多 20 条。评审者给主评保留全部已核实发现的编号、简述和证据引用，包括展示时省略的条目；主评在此基础上跨维度归并、排序。两个维度各自排第二的问题，可能对应同一项值得优先做的修复。对用户注明上限、实际列出数及有无省略；核实 3 个就列 3 个。达到 N 不代替关键路径核查，关键约束失守始终写入结论。

### 按具体结论标记置信度

| 置信度 | 怎么判断 | 在报告里怎么写 |
|---|---|---|
| 高 | 代码路径、契约、测试或运行记录直接支持这条结论，决定判断的关键条件已核实。 | 写明结论适用的版本、路径和依据。实现或契约已经足以证明时，无须线上复现。 |
| 中 | 现象已核实，根因或影响有具体证据支持，但仍有可能改变判断的条件。 | 可以作为有条件的发现进入 Top N；写清已知事实、尚待成立的条件，以及哪份证据能确认或推翻判断。 |
| 低 | 只有搜索命中、表面相似或未经核实的假设。 | 仅将可能改变档位、用途判断或行动顺序的线索列入「待核」，注明下一步用什么证据判别。同类候选合并，不占 Top N，也不计入已核实位置数。 |

归类时，分别判断共同现象、根因和影响。例如「3 处调用者按错误文本决定是否重试」可以是高置信度；若还没查过各调用者实际使用的 SDK 版本，「三处都因 SDK 缺少稳定错误码」仍是待核假设。只在各项证据强度不同时分别标注，无须逐位置重复同一标签。

置信度表示证据对结论的支持程度，严重性表示问题成立时的后果。两者不相乘，也不用置信度折算维度分数。低置信度线索若涉及关键约束，应在「待核」里优先说明要查什么；核实前不据此宣告约束失守。

## 分档与综合评价

先从已确认要求中区分关键约束与次要目标。**强**表示满足要求且设计有明确优势，须指出谁因此少承担什么风险、判断或成本；只证明达标，即使置信度很高，也应判**足够**。**有短板或隐患**表示关键约束仍成立，但已出现有实际影响的局部偏差，或有具体依据表明某个变化会带来风险；**不足**表示已有证据表明关键要求未满足。第三档要写明是「已发生」还是「可能发生」，分别给出影响或触发条件。可选优化本身不构成扣分理由。

维度内有已知也有未知时，保留已证实的优点和缺陷；若缺失证据可能改变该维度的档位，标为 **证据不足**，说明还要核对什么。若已有证据足以定档，则给出档位并注明剩余限制。不属于对象职责的事项标为 **不适用** 并说明原因。

按该维度对声明用途的实际影响定档，不按命中的示例数量取平均。同一事实只有在不同维度分别产生了可说明的影响时，才影响多个档位。例如，两处各自实现同一规则能说明职责分散；要据此下调可演进性，还要说明它怎样增加了代表性变更的协调成本。

总体结论分两步。先说**当前版本能否兑现声明的用途**：关键约束失守就指出受影响的用途；关键证据未齐就写「尚不能确认」及决定性证据。再说**缺陷是否源于架构**：保持现有契约、数据表示和职责边界，正确实现是否就能满足要求？若能，指出局部修复；若契约丢失必要信息或职责边界无法保证关键规则，再说明需要调整哪里。原因未明时保留待核，不降低已证实缺陷的严重性。例如字幕多显示一帧，可能只是边界比较写错；若接口只传整秒，调用方无法区分同一秒内的两帧，才有证据要求改变接口精度。其他维度的高分不能抵消这项用途的关键缺陷。

默认报告逐项分档。需要量化时使用上表的 100 分权重；如需按对象调整权重或移除不适用维度，在评分前说明依据，将适用维度的权重合计设为 100。横向比较要对齐用途、场景、范围、权重和计分规则。证据覆盖不同时，只比较共同核实的部分；待核项可能改变次序时，不给总体排名。

按档位乘以维度权重：强 100%、足够 80%、有短板或隐患 50%、不足 0%。汇总时同时保留各维度的依据。证据不足的维度先不计分，也不重分其权重；报告已评得分、已评满分及待核权重，如「已评 72/88，剩余 12 分待核」，不折算成完整总分。

主评交付总评及各维度报告（或可访问的引用）。总评说明适用范围、总体判断、值得保留的设计与行动优先级。跨维度问题按已核实的共同根因合并，引用原报告编号和位置清单；同一处去重，保留各维度的不同影响及其置信度。多份报告引用同一证据不会提高置信度。结论冲突时核对版本、场景和证据；裁决改变发现、范围或档位时，在原编号处同步更正或标注裁决，使单读维度报告的人也能看到有效结论。问题数不决定得分或全局排名。区分补证与修复：缺失材料可能改变结论时，写清应查哪条路径或哪份记录；只有达到特定规模、频率或故障条件才值得改时，写明触发条件。
