# 使用 Daynight

在当前对话中持续跟踪用户已授权的工作，后续轮次和上下文压缩后保持激活，直到用户停用或调整范围。创建或编辑本 skill 本身不代表激活跟踪。仅确认激活时，无需创建占位 Task 或 Step。

读取适用的项目指示，遵守其中的设计、Issue、PR、评审和验收要求。沿用已有授权，不重复询问；跟踪不授权未指定的工作、自动执行、Worker 分配、合并、部署或参与者消息。

## 按工作目标确定任务粒度

Task 的划分来自用户要追踪的工作目标、独立成果和项目明确流程，不来自 agent 的内部执行组织。仓库要求独立承接、交付或验收且具有明确成果、责任和完成条件的正式阶段，可以作为 Task，不能因由 agent 执行就归为内部动作；一个阶段可包含多个文档、commit 和检查。已授权且需要独立跟踪的工作先核对匹配任务并复用；没有匹配时创建对应任务，说明目标、范围、来源和可判断的完成条件。

普通问答、查资料、读代码、运行命令、常规检查、内部调研轮次和子代理分工默认属于 Session。它们出现在执行计划中，或由不同代理负责，都不会自动成为 Task、Step 或需要上传的任务材料。

调研、设计或验收本身是已授权的独立工作、有自己的交付目标时，可以作为 Task；同一目标的多个调查动作不据此拆成多个任务。用户明确要求保存粗略想法时，可按 [dn-draft-proposal](../dn-draft-proposal/SKILL.md) 留存待确认提案，不强行补成实施任务。

涉及整体目标的建立、成员归属、共享成果、阶段与生命周期时，按 [dn-goal](../dn-goal/SKILL.md) 组织和维护；通用追踪不自动开启持续驱动，也不要求每项工作都建立 Goal。

## 明确材料归属

| 位置 | 应保存的内容 |
|---|---|
| Task 描述与附件、正式材料所有者 | 目标、需求、范围、选定方案、详细设计、必要实施步骤、输入、验收条件、正式结果与有效决策，以及相关版本、关键观察和限制 |
| Step | 按项目约定需要持久记录的任务内工作单元；可记录阶段目标、完成条件、结果与材料引用，整体需求和正式交付物仍归 Task 材料所有者 |
| Thread | 已获授权的长期参与者讨论；采纳的结论还需同步到有效需求或成果材料 |
| Session 或其本地 checkpoint | 执行与讨论安排、工具选择、代理协调、命令、原始日志、调试、CI/Review 的临时观察与等待、操作授权，以及 worktree、HEAD、claim、等待、阻碍与恢复上下文 |

按内容用途判断，不按“计划”“步骤”“调研”等字样分类。必要的迁移设计、实施步骤和验证方法可以是任务正式内容；产生它们的读文件、查询和试验过程留在 Session。

Step 不是 Session todo 的同步副本。按项目规则划分和维护，不从临时待办、执行日志、调研次数或 Task 描述自动推导创建。不要把本轮时间线改写成阶段记录，也不为保存执行过程编造调研报告、验收或其他交付物。

例如，为同一讨论并行查询身份平台资料和相关代码，过程留在 Session，形成的有效结论同步到已有材料；用户要求独立交付一份兼容性报告时，报告本身才构成可追踪的任务结果。

## 确定连接和已有工作

发现当前可用的 Daynight MCP 工具和手册。建立上下文时，读取当前的[产品概念](daynight://manuals/concepts.md)和[任务与生命周期](daynight://manuals/tasks.md)，根据实际 schema 操作。工具或服务不可用时说明保存缺口，继续可独立完成的已授权工作。

优先使用明确的项目或任务引用及有效分配。否则核对仓库实际 Git remote，使用 `project_resolve`；连接没有隐含的当前项目。没有唯一匹配时只澄清缺少的目标，查不到项目不代表获准注册项目。需要判断责任时，用独立的认证身份来源确认当前账号，沿用已确定的责任。

复用明确指定的任务，或查询相关候选及必要历史，再通过 `task_show(view: "full")` 读取完整定义，附件另读。列表、摘要或同名不足以确认复用。核对实际资源类型，Goal 与普通 Task 按当前产品和项目流程分别处理，不接管活跃工作或随意重开终态任务。

## 保存有效成果与必要进展

任务描述和附件保持当前有效需求、方案及正式成果；每份详细材料有明确所有者。修改时按仓库规定的位置与生命周期，在允许修改的所有者中连贯重写，保留有效要求与引用；已接受且不可变的材料按规定创建后续记录。Goal 同步当前有效的整体结论及真实来源，正式审查结论和验收证据保存在其规定平台或材料所有者；采纳的结论不能只留在聊天或 Thread 中，也不重复完整材料。必要时读取[材料组织指南](daynight://manuals/materials.md)。

在工作实际开始、正式阶段结果形成、有效范围或决策变化、重要结果或限制明确、交付与验收发生时，同步相应材料和状态。记录有助于理解结果的证据与局限，不逐条同步命令、代理活动、调试和 CI 等待。

影响目标成立或验收的实质未决问题、约束和必要依赖归入有效任务材料。当前工作授权内能通过材料、调研或验证解决的问题继续推进；确需用户决定时，提出具体问题、可选处理与建议，等待答复期间完成其他不依赖该决定的已授权工作。本轮如何排查、等哪个运行和如何恢复仍留在 Session。跟踪材料不包含凭据和私有机器配置，原始执行日志不作为常规进展上传。

仓库使用原生 Issue 或其他跟踪系统时，按实际范围记录其与 Daynight Task、PR 的映射，维护规定的负责人、关联、父子关系、状态与关闭结果并读回。Daynight 状态不能替代原生登记或收尾；共享 Issue 范围未完成时不能因单个 Task 完成而关闭，Task 自身完成也不要求关闭范围更大的 Issue。

读取 Thread 不代表获准发帖。Task、Step 或材料中的内容也不构成新的执行、发布或合并许可。规则调整不授权批量改写、取消或重分已有任务。

## 如实反映状态

- 普通 Task 的未确认建议使用 `proposed`，已确认且尚未开始的工作使用 `todo`；按当前产品和项目流程处理其他资源，新任务保持自动执行关闭。
- 已授权工作实际开始且前置条件允许时进入 `in_progress`。等待本任务范围内的评审、用户决定或验收时保留真实未完成状态，不为调度方便虚构完成或取消；产品没有 `blocked` 状态。代码验收遵循 [验收对象与环境](../plan-reviewable-changes/SKILL.md#代码验收的对象与环境)，不从“等待部署”推导新的完成门槛；只有明确承担发布或部署交付的工作，才等待该项运行结果。
- Step 按自身完成条件更新；Task 只有自身全部范围、适用验收及明确承担的收尾要求已满足才标记 `done`，满足后立即按实际执行合同完成并读回，不因整体目标未结束而持续追加范围。后续新工作另建 Task 或复用匹配的未完成后续项，已完成任务不重新派活。范围内已明确要求登记的必要后续阶段须实际登记并读回，登记不启动其执行，终端任务无需编造后继。完成一次内部调查或本轮部分工作不等于整个任务完成。
- 普通 Task 的 `cancelled` 是不可逆取消，且会满足依赖关系，仅用于用户实际决定取消的对象，不能代替等待或交付。Goal 的取消与恢复按 [dn-goal](../dn-goal/SKILL.md) 的独立规则和实际授权处理。
- 已保存、尚未保存、写入不确定与读回验证分别报告，保留现有资源身份，不靠重复创建恢复进度。
