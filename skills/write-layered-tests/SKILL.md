# 编写分层测试

按被验证的行为确定测试范围，以可信、快速和易维护为目标。代码分层明确职责归属，测试可以包含一组内聚的真实协作者；不把每个文件、类或层次机械变成 mock 边界。

优先执行快速、确定、易于准备和清理的真实下层逻辑。对昂贵、不可控，或需要精确提供结果、错误和时序的依赖使用替代。最底层机制保留真实依赖测试，再用少量 API 集成和完整 E2E 验证真实组装。阅读 [Client/Server 示例与图解](references/client-server.md)理解这些范围。

## 按目标选择依赖边界

**先判断依赖方向，再决定用真实实现还是替代。** 单元测试从被测模块自己的入口触发目标行为，只使用本层能力、架构允许的依赖及中立测试设施。不得反向依赖被测模块的上层生产调用方；数据准备、执行、断言、读回和清理都受此约束，包括经 fixture、helper、测试工厂或上层专属测试包引入的间接依赖。把上层调用方换成 mock 也不能使方向合法。被测模块本就依赖的共享契约、直接构造的数据和独立的数据库 fixture 可以使用。

在方向合法的协作者中，按下表选择边界。同一入口的不同测试可以因验证目标不同，选择不同的真实或受控依赖。

| 情况 | 选择方式 |
|---|---|
| 轻量、确定的规则、转换、解析或内聚流程 | 优先运行真实实现，避免重复维护协作者行为 |
| 耗时、重计算、昂贵环境、外部副作用或难以稳定复现的协作者 | 在有明确语义的能力边界替代，控制必要结果 |
| 需要特定冲突、失败、阻塞、时间或取消状态 | 即使操作很轻，也可替代直接操作或所需能力，使目标行为易于触发和观察 |
| 协议映射、业务编排或生命周期专项 | 根据目标选择直接业务操作处隔离，或保留一组简单的真实协作者 |
| 算法、数据库、文件、传输或生命周期机制本身 | 执行真实被测机制；纯函数直接构造输入 |

例如正常业务测试可以控制 DAO 结果，真实执行 Handler → Service → Core；HTTP 错误映射测试则可以直接提供 Service 冲突结果。不要为了维持某种层次形式，搭建庞大的数据准备或逐项 mock 调用链。

Mock、stub、fake 或注入函数只控制当前断言需要的能力。重计算本身是测试对象时仍执行真实算法；上层仅使用计算结果时可以替代该协作者。替代不能冒充对真实机制的证明。

## 按职责组织断言

完整的业务规则、边界、拒绝、错误、取消、并发和恢复场景归负责它们的模块。上层保留所需的调用者行为测试，不重复所有下层规则矩阵。

审查时从测试入口和辅助函数各追一遍：如果只改上层业务流程、保持被测契约不变，这条测试会不会因为用了上层而失败？若断言属于本层，只是借上层造数或读回，就保留测试和断言，将这些步骤换成本层操作或中立 fixture。若断言验证的是上层承诺（如权限拒绝或 HTTP 状态码），把该项验证移到对应上层。混合测试按断言拆分，SQL、锁和事务等独有保证仍由 Store 直接验证。

优先断言可观察结果、状态变化和有意义的副作用。调用次数、顺序和参数只在影响正确性时验证，例如协议拒绝后不调用业务、写入不重复、事务绑定正确、取消后工作退出。避免把完整内部调用轨迹当作对外约定。

受控替代只实现当前测试需要的能力，未配置的意外调用应暴露失败；不要默认返回空结果掩盖错误。保持 case 状态独立，避免依赖前一 case 的结果。真实下层缺陷导致上层测试失败属于检错范围，不能据此认定执行不稳定。

## Go 单元测试代码组织

- 单元测试代码与被测代码放在同一目录，使用 `*_test.go` 文件，命名应能识别对应的被测对象。
- 原则上，一个被测对象的单元测试集中在一个测试文件中。该测试文件超过 1000 行时，可按功能或场景酌情拆分成多个文件，保持清晰的归属。

## 用真实外部依赖验证机制

外部适配器拥有自己的真实依赖测试。数据库访问层连接与生产使用相同引擎的真实、隔离的数据库实例，执行实际 SQL，验证映射、持久化读回、约束、事务、锁、迁移和相关失败或并发行为。内存替代实现和受控查询结果不能证明这些数据库保证。

其他外部机制使用其所需的真实资源，环境由测试管理。生产资源和共享开发资源不能充当 fixture；缺少基础设施时明确记录验证缺口或让检查失败，不能静默变成通过。

## 保留 Server API 集成和完整 E2E

Server API 集成通过 HTTP 测试客户端访问真实 Server，贯通路由、业务、数据访问和真实外部依赖，验证服务端组装及持久化链路。

完整 E2E 从真实 Client 的公开入口发起，贯通 Client、真实 Server 和真实持久化，验证功能主流程。检查同一资源的身份、内容、状态变化和后续读回。

两者各自选择少量代表性的正常流程；一般功能用一条主流程，实质不同的组装路径再增加场景。模块或组件测试承担完整的规则、错误和竞态矩阵。

服务与客户端独立升级时，依据已确认的支持矩阵与风险，验证新服务配受支持的旧客户端，以及支持政策要求的新客户端配旧服务等关键组合，覆盖既有操作、新能力条件和不匹配行为。同源码版本的 E2E 不能单独证明版本共存；证据绑定实际发布版本或经核对的原始协议与解析实现，不能仅模拟宽容解析就宣称旧客户端兼容。无法取得必要版本或环境时保留具体缺口，不把同版本通过充当替代；不要求测试所有历史版本的任意组合。

## 复用昂贵的初始化与清理

当环境构建、schema 初始化、进程启动或清理成本较高时，在职责相关、生命周期明确的测试组内复用基础环境，以组级 setup/teardown 分摊成本。每个独立 case 从已知初始状态开始，case 级只承担必要的数据准备与状态恢复。例如数据库 case 可共享 schema 和连接池，在 case 之间恢复数据及序列状态，组结束后统一关闭和销毁。

复用以 case 可单独选择、重复执行和调整顺序为边界。前一 case 的工作与清理完成后，恢复所有可能影响后续执行的可变状态。共享可变资源的 case 顺序执行，或建立可验证的并发隔离。难以恢复环境或专门验证资源创建与销毁的 case 使用独立资源；重置失败、资源未释放或状态无法确认时停止复用并报告错误。

保留真实提交、持久化读回、跨连接观察和并发机制。评价收益时计入重置与最终清理成本，并确认原有断言及缺陷检出能力保留。

## 缩短不影响可信度的固定等待

轮询、重试、延迟触发等固定等待，在不改变被测行为和缺陷检出能力的前提下，通过注入或 mock 缩短时长，也可用受控时钟推进。

保留真实控制流程和必要的顺序、调用次数、取消及超时断言。生产默认时长属于约定时单独验证原值及传递。通过事件或同步屏障确认目标阶段，避免过短期限依赖机器调度速度；真实计时和外部系统行为仍由对应机制测试证明。

## 检验执行与维护成本

模块或组件测试、真实依赖测试、Server API 集成和 E2E 使用明确的入口或选择方式。编写或调整测试后，实际执行新增、变更及受影响的必需检查；失败后查看原因，修正当前授权范围内的问题并重新验证，遵循项目重试约定。一个入口通过不能代替其他必需检查的结果。

缺少环境时，先寻找已有的合适隔离资源，完成当前范围内已授权、成本合理的准备，再继续验证。完成可行的检查后，确有无法自行解除的阻塞才报告具体缺口及最小所需输入。只读测试审查保持只读，以完成相关覆盖核查和可行验证为结束条件。

为环境启动和执行设置期限，各作用域在成功、失败或取消后清理自己的进程、连接、存储和全局状态。共享资源在所有使用者退出后由所有者释放，保留测试和清理失败。

调整测试边界或迁移场景时，先确认接收测试实际运行并保留每项独有保证，再移除原有覆盖。同时评价执行时间、fixture 复杂度、重构时的修改量、失败定位和缺陷检出能力。
