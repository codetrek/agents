# 起草 Daynight 提案

把一组相关的粗略想法整理成可继续讨论的 Daynight 任务。这里的 proposal 是普通 Task 的 `proposed` 状态，表示尚未确认的建议，不是已排期的实施任务。

## 保留想法的成熟程度

收集用户已经表达的方向、背景、期望和约束，区分实际观察、用户判断、初步假设和待确认事项。只问完成登记真正缺少的信息，不为记录想法强行调查根因、选定方案或补齐实施设计。

每个 proposal 围绕一个问题或方向；相关想法可以归为一项。明显无关的想法先简要分组，按用户给定的数量与范围登记，不自动扩展成 Goal、讨论阶段或交付子任务。

标题概括待讨论的方向，描述保留理解它所需的内容，按已有信息组织，不使用空模板：

| 内容 | 记录方式 |
|---|---|
| 想法与期望 | 想改善什么，初步期待达到什么效果 |
| 背景与动机 | 已知场景、用户感受到的问题及其影响；未经核实的内容明确标注 |
| 约束与线索 | 用户已给出的限制、相关任务或资料，说明引用是否已经核对 |
| 初步方向 | 有则记录为候选，不把猜测写成已选方案 |
| 待确认事项 | 尚不清楚的问题、取舍和后续需要了解的内容 |

最终需求、详细设计、实施步骤和验收阈值可以尚未确定。不要把建议改写成确定的根因、实现承诺或已经验证的收益；提案无需达到交付任务的派发门槛。

## 确认项目与已有提案

读取目标项目的约定，沿用明确的项目引用或当前仓库的实际关联。通过当前 CLI 或 MCP 工具确认服务、账号和目标项目；CLI 的操作与参数以 `daynight --skill` 和相关 `--help` 为准。项目缺失或有歧义时只解决必要的目标选择，不擅自创建项目。

查找同一问题或方向的已有任务，包括历史结果，再读取相关候选的实际类型和完整描述。标题或搜索摘要不足以判重，必要附件单独读取。相同 proposal 已覆盖想法时直接复用；需要补充时只在授权范围内更新，保留仍有效的目标、内容与责任。

不要把已确认、执行中或已完成的任务改回 `proposed`，也不覆盖别人的内容。历史工作与当前想法确有不同之处时写清区别；不能只因状态不同就重复登记。用户仅要求讨论时先在会话中整理，不把讨论自动变成写入授权。

## 登记并读回

按实际工具 schema 新建普通任务，明确选择 `status=proposed`，新任务保持 `allowAgents=false`。负责人沿用产品默认或用户明确指定的安排，不擅自转交他人；未确认的平台、依赖和 Worker 选项不预设为执行要求。

内联描述足够时不额外创建附件。确需附件时上传并读回，再加入真实引用；描述保留有效内容，避免依赖原聊天或临时私有文件。更新既有任务使用最终读取的准确版本，冲突后重新判断，不盲目替换版本重放。

保留返回的任务 ID，完整读回核对其为普通 Task，内容、项目、所属关系、状态、负责人和权限与登记意图一致。创建响应不确定时结合原操作上下文、完整字段和资源身份核对，不能凭同名任务或一次空查询重复创建。材料保存或读回失败时报告已完成部分与缺口，不声称已完整登记；并发状态变化按实际观察报告，不自动回退他人的操作。

返回任务引用、已保存的想法摘要和主要待确认事项，然后结束。完成登记不把任务标记为 `done`，不改成 `todo`，不开启自动执行，也不自动创建或启动后续的正式需求、方案或实施任务。后续推进按用户新的请求或已有明确授权进入相应流程；需要正式梳理需求时，可使用 [my-write-spec](../my-write-spec/SKILL.md)。
