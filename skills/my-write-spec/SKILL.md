# 编写需求规格

主动推进当前已授权的规格工作，形成独立可读、明确且可验证、可供用户整体确认的完整需求，为后续方案设计与验收提供依据。内容深度随问题规模调整，不靠固定章节、篇幅或条目数量判断完整性。用户明确限定为草稿或局部讨论时，按该范围完成。

## 确认规格工作与任务状态

读取用户请求、已确认要求和相关材料，确定当前需要会话讨论、规格草稿还是修改正式文档，沿用已有授权并遵守项目的语言、文档位置、任务管理及工作区约定。编写规格不自动启动架构设计、实施、任务派发或 PR、Issue 交付。

项目用 Daynight 跟踪规格工作时，按项目规则找到对应的需求任务；需要为已授权的规格工作新建任务时，显式指定 `todo`。实际开始撰写或修订规格时，在前置条件满足且有权限的情况下，把对应任务置为 `in_progress` 并读回核对；已在该状态时无需重复更新。规格是草稿或仍待用户确认，任务仍可处于 `in_progress`。仅登记尚未确认要开展的建议时使用 `proposed`；复用已有 `proposed` 任务时，按项目规则确认是否可以接受并启动。

核对必要的现状、受影响的使用者和既有行为。区分实际观察、用户报告、目标、建议和假设，不把现有实现当成必须保留的需求，也不把未验证的原因写成事实。需要调查时按问题委派研究代理，明确证据范围和缺口。

## 梳理需求与开放问题

先从已有上下文提取可确定的内容，再集中提出会影响范围、行为、约束或验收的关键问题。能由现有材料回答的先核对；给用户具体场景和选项，避免泛泛访谈或反复询问已经确认的要求。

需求说明必须达到的结果与约束。用户提出的接口、数据格式或技术条件，区分硬性要求与候选建议，并保留其来源；存在冲突时明确提出。尚未决定的数据库结构、协议编码、模块拆分和实施步骤留给方案设计，不自行补成需求。

涉及独立升级的服务与客户端时，明确版本支持范围、服务升级后已发布客户端应保持的行为、新能力对升级的要求，以及弃用或中断支持的条件。复用现有支持政策；尚未确定的实质取舍主动提问，不默认所有客户端同步升级，也不擅自承诺所有历史版本永久可用。具体协议演进机制留给方案设计。

草稿可以暂时保留未知项，但每项关键缺口须主动推进：能由已有材料、调研或验证确定的继续查证并补齐；确需用户决定的，提出具体问题、可行选项、影响与建议，等待答复期间完成不依赖该决定的内容。收到答复后同步规格并继续收敛，不等用户追问才推进。明确哪些要求已确认、哪些仅是建议、哪些仍需决定；不要用默认值、猜测或含糊表述替代关键决策，也不为了填充模板增加功能。

## 写出可独立阅读的规格

按实际需要覆盖以下内容，可以合并章节，已有定义引用其所有者：

| 内容 | 应明确的事项 |
|---|---|
| 背景与目的 | 要解决的问题、目标使用者、当前影响及期望结果 |
| 范围与边界 | 本次承担的结果、明确不包含的内容和必须保持的既有行为 |
| 角色与场景 | 谁在何种条件下发起什么操作，以及期望获得的结果 |
| 功能行为 | 前置条件、输入输出、状态变化、可见结果和必要的副作用 |
| 异常与边界 | 适用的拒绝、失败、取消、重试、并发或恢复行为 |
| 约束与质量要求 | 实际相关的权限、数据生命周期、平台、容量、性能、可访问性等约定 |
| 验收条件 | 证明要求满足的条件、操作或输入、预期结果与必要验证环境 |
| 待确认事项 | 尚未解决的问题、影响和需要谁决定 |

围绕行为写清主体、条件、动作、时机、顺序及后果。用必要的例子、数据或交互流程消除歧义。UI 需求说明适用状态与交互，原型及资源按用户和项目要求提供并验证，不为无关场景强加原型。

“更快”“更易用”“支持大规模”等目标需要落实为可判断的结果。确需数值指标时明确单位、负载、测量条件及依据；阈值未确认就标明待定，不随意承诺性能或容量。

验收覆盖关键成功、失败和边界行为，与需求逐项对应；复杂规格可用稳定编号建立关联。验收描述可观察结果，测试类型和实现手段由后续验证设计确定。保留用户明确的接口与格式约定，不复制已有 schema、协议或类型目录。

## 核对完整性与一致性

检查目标、范围、场景、行为和验收是否一致：每项重要要求都有判断方法，验收不引入额外功能，角色与术语一致，状态、权限、错误和数据变化没有相互矛盾。只覆盖已确认目标，避免把潜在扩展当成必需能力。

根据项目要求和实际风险安排独立需求核对，提供原始意图、当前版本、确认范围和依据。核对完整性、歧义、冲突及可验证性，不用架构偏好扩大需求，也不按缺少某个标题判定需求无效。对已确认要求和证据能够确定的缺漏、冲突或不可验收表述，主动修订完整当前规格并复核；不能把核对结果仅作为缺口清单交回用户。

完成所有可独立推进的内容后，关键范围、行为或验收仍需用户决定时，主动提出具体决策问题并报告当前草稿状态。草稿和待确认标签不构成停止已授权工作的理由；仅在当前要求的成果已完成，或确有必要输入、实质决定或外部条件无法自行取得时结束，并说明最小所需条件。材料写完、代理评审通过与用户确认是不同事实；不能代替用户决定。

## 保存、确认与后续边界

按约定交付完整当前材料。修改既有规格时，先遵守仓库的材料归属、接受与变更流程，在允许修改的所有者中整份连贯重写，同步受影响的摘要、原型和引用，保留有效要求与必要理由；已接受且不可变的材料按规定新增后续记录，不能直接覆盖。会话日程、工具活动和评审过程不写成需求。

项目要求任务描述、附件或特定规格文件时，在请求确认前保存并读回，检查实际内容和引用可用性，提供真实位置。保存或读取失败时先核对实际状态，完成可恢复且已授权的处理并重新验证；确实无法恢复时说明具体缺口，不能把会话摘要当作已保存的正式规格。

用户确认针对可读取的当前完整版本及适用资源。实质需求变更后重新确认受影响的当前规格；编辑措辞不自动重开已确定事项，也不把先前版本的确认套用到新行为。

返回材料引用、确认状态、主要待决策事项及当前阶段结果。需求确认不自动授权方案设计或实施；用户要求推进时，按项目流程把确认规格作为 [my-architect-and-design](../my-architect-and-design/SKILL.md) 的输入。
