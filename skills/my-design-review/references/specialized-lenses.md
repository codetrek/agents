# 专项判断要求

## 性能与资源

先确定相关数据规模、调用频率、并发、热路径及延迟、内存或其他资源预算。区分实际测量、复杂度分析和待验证假设；无法测量时明确验证方法与缺口，不编造收益。

复杂度、嵌套循环、分配和 I/O 是调查信号，不自动形成 finding。有界小集合可以采用简单算法；缓存是否有益取决于复用、失效、权限和维护成本。按实际需要比较完整成本，不默认增加缓存、索引、并行或面向百万用户的结构。

只有能说明相关负载下的具体问题、必要预算未满足或合理证据缺口，才给出对应严重程度和建议。

## 模型工具表面

核对用户目标、资源身份、完整字段、版本与前置条件、确认步骤、权限和失败语义。成本优化必须保持这些约定，不能为了缩短描述、输出或往返而破坏功能或降低必要准确性。

按目标平台和实际加载方式分析描述与 schema、输出规模、往返次数及 token、延迟和准确性。使用当前可核对的平台限制和项目测量，不引用固定的私有报告路径或把某个 API 的限制推广到所有宿主。

实际收益用代表性数据证明；设计阶段尚未测量的假设记录为验证项。只有违背必要语义、必需预算或关键有效性要求时才作为重大问题，不因输出是原始数据、需要多次调用或存在未测估算而自动判为 Critical。
