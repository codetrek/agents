# 设计方案评审

判断当前方案能否满足已确认目标，以及哪些问题需要修正或决策。评审围绕实际约定、可观察后果和证据，保持独立，不预设必须增加模式、缓存、抽象或删除代码。

## 确定范围、阶段与依据

沿用当前请求和已有授权，明确评审的是候选方向、方案草稿还是待实施设计，以及具体目标与范围。评审默认读取输入并交付约定的结果，不授权修改设计、业务代码、Git 状态或发布评论。

读取当前设计及相关原始材料：已确认要求、项目规范、相关实现与调用者、schema、文件格式、协议、公开接口和共享类型定义，以及验证与交付安排。设计中的自述不能替代这些依据。按实际影响查证，不无差别审计整个仓库。

按 [简单方案与复用要求](../my-architect-and-design/SKILL.md#优先采用简单可行方案) 核对整体架构是否合理，以及现有能力的复用、扩展或必要重构是否合适。新增机制或协议应对应具体要求与真实缺口，并与能满足要求的简单方案比较整体成本。发现可用的简单方案被忽略，或为少改代码而叠加特判、旁路和临时适配时，给出具体依据与范围内的调整建议；必要的安全、正确性、版本支持及生命周期保证仍须保留。评审建议新增机制也遵循同一依据，不将更多模式、状态或协议视为方案更完整的证明。

将所有 reviewer 绑定到同一文档版本或内容 hash；输入变化后核对结论是否仍适用。区分已验证事实、设计选择、估算和假设，缺失的证据明确记录。按设计阶段判断：早期方案可以保留验证计划，待实施设计需要明确影响其成立的关键约定与验证条件。

## 按风险选择独立视角

使用实际可调用的独立代理，按设计涉及的风险分工；多个视角可以由同一独立 reviewer 覆盖，不机械要求固定人数或完整角色清单。作者自查不能替代独立评审。工具、模型、权限、期限和结果合同遵循 [评审执行要求](references/execution.md)。

| 视角 | 核对重点 |
|---|---|
| 架构与边界 | 模块职责、依赖、持久化与交换格式、公开接口、共享类型及其所有权，权限、一致性、迁移和生命周期 |
| 可维护性与实施 | 方案是否可实施，交付单元的规模预测与安全切分是否成立，复杂度、代码组织与错误处理是否符合实际需要和项目约定 |
| 验证策略 | 候选版本、受控验收环境、构建启动和执行责任是否明确，所需行为能否被可信验证，真实与受控依赖边界、错误和竞态覆盖、集成与 E2E 是否适用 |
| 性能与资源 | 实际规模、频率、热路径和资源预算，以及方案的完整执行和维护成本 |
| 运行与观测 | 异步边界、上下文、取消、失败、资源归属和实际可查询的观测证据 |
| 模型工具表面 | 仅在涉及模型工具时，核对必要语义、输入输出、往返成本、准确性和实际平台限制 |

代码结构参考 [code-structure](../code-structure/SKILL.md)，验证参考 [write-layered-tests](../write-layered-tests/SKILL.md)，交付边界参考 [plan-reviewable-changes](../plan-reviewable-changes/SKILL.md)。设计材料的要求参考 [my-architect-and-design](../my-architect-and-design/SKILL.md)，运行观测按其 [可观测性要求](../my-architect-and-design/references/observability.md)核对。性能或模型工具评审阅读 [专项判断要求](references/specialized-lenses.md)。这些引用用于核对相关约定，评审按当前范围执行。

涉及独立部署的服务和独立分发的客户端时，按 [独立发布与版本共存](../my-architect-and-design/SKILL.md#独立发布与版本共存) 核对支持范围、升级顺序、已发布客户端行为及版本组合验证。把“用户会同步升级”作为前提、仅凭同源码 E2E 宣称兼容，或将数据库旧数据迁移等同于客户端升级，均需按实际影响查证；不能自动要求所有端同任务、同 PR 或同时部署。支持政策未明确时记录具体决策缺口，不凭评审偏好要求无限兼容或额外的固定协商机制。

按 [验收对象与环境](../plan-reviewable-changes/SKILL.md#代码验收的对象与环境) 检查验收方案能否对实际提交执行。E2E 应有验收方负责的服务、客户端及依赖准备和版本证据；把线上实例或 Release 当作候选代码、留下无人负责的“部署后再验证”，应指出其造成的错误前置或不可执行缺口。必要的真实集成与版本组合验证仍须保留。

## 形成有依据的 finding

每个 finding 说明：

- 对应的设计位置及受影响的要求或不变量。
- 会出问题的具体场景、后果和可核对的依据；尚未证实的部分明确标注。
- 严重程度、最直接的修正建议，以及范围内修正、延后、不成立或待决策的处置。

| 严重程度 | 判断依据 |
|---|---|
| Critical | 方案存在严重安全或数据完整性问题，或根本不能成立且会造成严重后果 |
| Major | 主要要求不满足、关键约定矛盾，或缺失必要定义与验证导致不能可靠实施 |
| Minor | 局部质量改进，对当前目标没有实质影响，不作为阻塞项 |

严重程度根据具体影响判断，不由缺少章节、模式、缓存、某种复杂度或代码新旧自动决定。验证策略可以存在于正文、引用材料或既有测试中；按实际行为和机制选择所需测试类型，不强制每个设计都有所有测试类别。

先核实 finding 是否成立和属于范围。新增能力、无关清理与较小建议延后；需要用户选择或缺失证据的事项单独保留。兼容与迁移依据已确认要求和实际消费者判断。不能用评审优先级扩大设计目标，也不为凑建议数量提出改动。

## 汇总当前版本的结论

验证实际参与的 reviewer 已完整结束，结果属于当前输入；失败、取消、部分结果与必要视角缺失按照执行要求处理。只列真实完成的参与者和模型，不为未运行角色生成 verdict。影响结论成立的覆盖缺口必须明确。

去重并核对重要分歧，保留有依据的 Critical/Major、待决策事项和必要证据缺口。压缩表达，不按固定建议数量删掉重要 finding，也不靠赞扬、删除机会或过程叙述填充报告。

结果区分评审是否完成，以及设计在该范围内是否存在重大问题、需要修改或仍需决策与证据。范围内未发现 Critical/Major 不代表用户已接受设计，也不授权实施。重大问题或影响成立的缺口不能包装成批准。

只在约定的作用域保存结果，遵循项目的语言、材料所有权和 worktree 规则；可以返回文本由调用者保存，不强制写在设计文件旁边。需要长期保存的材料写入后读回并提供真实引用。

设计修改与重新评审由已授权的设计流程协调。关键机制改变后重新核对受影响内容，旧版本的结论不能直接作为新版本通过的依据。
