# 代码结构规范

按层次分离职责，按功能组织代码。相关代码集中放置，不同职责明确分开，让目录、文件、类和函数都保持容易理解和维护的规模。

## 按层次组织

服务端通常按以下职责分层，Client、CLI 和其他程序采用适合自身的对应层次：

| 层次 | 职责 |
|---|---|
| API 协议 | 请求、响应、数据格式与接口约定 |
| API Handler | 请求解析、调用业务操作、响应转换与协议错误映射 |
| Service | 用例流程、跨模块协作与业务操作编排 |
| 核心模块 | 各业务领域的规则、算法、权限判断与状态转换 |
| 基础设施 | 数据库、网络、文件和外部系统的实际访问 |

明确调用与依赖方向，避免循环依赖。核心逻辑独立于 API Handler、UI 等入口细节。层次按实际职责设置，避免为每个方法机械增加没有职责的转发层。

## 按功能拆分过大的代码单元

| 出现的问题 | 调整方式 |
|---|---|
| 一个目录中的文件过多或混杂多个模块 | 按业务模块或功能划分子目录，相关文件归入同一模块 |
| 一个文件过大或包含多组独立功能 | 按功能拆成多个文件，保留清楚的模块入口 |
| 一个类过大或承担多个职责 | 按功能拆成职责明确的类，通过组合协作 |
| 一个函数过长、嵌套过深或包含多个独立步骤 | 提取有独立含义、输入输出明确的函数，由上层函数组织流程 |

规模是检查和拆分的信号；结合职责数量与理解成本判断，不机械套用统一的文件数或行数阈值。按功能边界拆分，避免只把长代码切成需要反复跳转的碎片。

## 保持结构清楚

- 目录、文件、类和函数的命名应准确反映职责；同一层次的命名与组织方式保持一致。
- 每项业务规则有明确归属，调用者通过模块能力复用，避免复制规则。
- 共用代码按实际用途抽取，避免把无关功能堆进 `utils`、`common` 或万能 `Service`、`Manager`。
- 拆分后的单元通过明确的输入输出与组合协作，减少隐式依赖；结构重构保持既有行为，并同步受影响的调用者和测试。
