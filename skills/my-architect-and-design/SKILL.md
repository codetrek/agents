# 架构与方案设计

围绕已确认的目标形成有依据、可实施、可验证的方案。设计的深度与问题规模相匹配，明确职责、关键约定和真实取舍。

## 确定目标与操作范围

从当前请求和已有授权区分讨论、设计文档修改、独立评审、PR 或 Issue 等交付，以及代码实现。沿用已有授权，不因进入下一阶段重复确认；设计或评审通过本身不授权实施、发布或扩大范围。

阅读适用的项目指示和材料所有权规则。语言、文档位置、命名、决策记录、任务管理和 worktree 使用遵循项目与用户约定；讨论请求保持讨论范围。需要用户决策时，先形成具体选项和可审查材料，继续不依赖该决策的已授权工作。

目标仓库明确的开发与 PR 流程、材料归属、生命周期和已有例外优先于通用设计流程，仍遵守指示优先级与当前授权。将必需的设计交付、审查和验收阶段纳入当前方案与拆分，复用覆盖当前范围的已接受成果。

使用 Daynight Goal 组织本次目标时，按 [dn-goal](../dn-goal/SKILL.md) 核对当前阶段、共享材料所有者、实际子任务与整体验收，设计产出的有效整体结论同步到 Goal；这不启动 Goal 的持续执行。

需要先梳理需求时，使用 [my-write-spec](../my-write-spec/SKILL.md) 明确目标、行为与验收；在项目流程允许的范围内复用已有确认要求，不为文档形式重复开展需求阶段。

## 探索现状与必要依据

先检查相关实现、调用者、既有约定、测试和运行机制，判断现有结构是否适合当前目标，明确哪些能力可以复用、合理扩展或通过必要的职责调整满足需求。按实际问题委派独立研究代理；可并行的调查按主题分工，共享任务允许的工作区域，避免重复调查和并发改写同一材料。

区分现状事实、外部依据、方案假设、测量结果与估算。现状引用可核对的代码或文档，外部技术结论优先使用原始文档与研究，性能和行为结论说明测量范围及限制。工时估算使用分钟。证据不足时明确缺口，不用推测补成已验证结论。

## 优先采用简单可行方案

以整体架构合理、职责清晰、依赖与关键约定一致为前提，优先复用现有机制，寻找能完整满足已确认要求的简单方案。现有结构不适合时，在当前目标范围内合理重构、调整职责或替换不合适的机制，不能为了少改代码、维持原结构而叠加特判、旁路和临时适配。简单程度看整体概念、状态、协调关系、失败路径及使用和维护成本，不能只按代码行数或改动量判断，也不能靠省略必要保证换取表面简单。

只有现有机制及合理的简单调整存在具体不足时，才引入新的机制或协议。说明哪项要求无法满足、现有能力为何不适用，以及新机制如何弥补缺口，并计入实现、测试、迁移、运维和长期维护成本。不能仅以“更通用”“以后可能需要”或模式惯例作为新增理由；复用也需符合真实语义，避免为复用而扭曲现有职责。

技术选型比较真正可行的备选方案及其取舍，保留简单候选及其采用或排除依据；不凑固定数量，也不为小改动制造复杂选型流程。已确定的约束和方案不因模板而重新开放。需要实验时，在授权范围内验证关键不确定性，并清理自己管理的临时资源。

## 形成方案与交付单元

任务拆分、breakdown 或交付单元规划时，仓库没有明确要求的部分，优先使用 [plan-reviewable-changes](../plan-reviewable-changes/SKILL.md)；仓库已有要求的部分，在满足仓库规则的前提下结合该 skill，确定合理的单元边界、规模、验证和交付顺序。

根据问题选择必要内容，简短设计可以合并章节，复杂设计按职责展开：

| 内容 | 应说明的事项 |
|---|---|
| 问题与要求 | 已确认目标、范围、约束和可观察的完成条件 |
| 现状与取舍 | 相关机制、真实备选方案、推荐理由和尚未验证的假设 |
| 设计机制 | 模块职责、依赖方向、业务规则、权限、状态变化、错误和必要的一致性及生命周期 |
| 数据与边界约定 | 本次涉及的持久化格式、关键存储访问路径与约束、交换协议、公开接口和模块共享结构 |
| 验证策略 | 候选提交或制品、组件版本组合、被验证行为、验收环境与执行责任、构建启动方法、真实与受控依赖边界、失败及并发场景、集成主流程与证据 |
| 交付拆分 | 仓库必需阶段、各单元的成果与边界、适用代码及审查规模预测、验证、阶段完成条件、前置与安全顺序；较大组合的更小候选及不可拆依据 |
| 风险与待决策 | 会改变方案成立条件的风险、证据缺口和需要用户决定的事项 |

代码及端到端验收遵循 [验收对象与环境](../plan-reviewable-changes/SKILL.md#代码验收的对象与环境)，并使用 [plan-actionable-verification](../plan-actionable-verification/SKILL.md) 在方案阶段确认执行者、环境能力、输入来源及前置责任。关键条件无法落实时，调整验证路径或保留为明确缺口。

需要时用图和数据或接口示例澄清关键机制。代码结构参考 [code-structure](../code-structure/SKILL.md)，测试参考 [write-layered-tests](../write-layered-tests/SKILL.md)。

### 数据结构与边界约定

持久化格式、交换协议、公开接口和模块共享结构属于架构设计范围。本次新增或改变的关键定义应在实施前明确；已有且未变的定义引用其所有者。按实际涉及的内容说明：

- 数据库与磁盘格式：相关实体、表或文件，关键字段的类型与语义、身份和关联、关键访问路径与约束、格式版本、读写与发布边界，以及迁移和恢复。
- 网络协议：通信双方、消息结构、交互顺序、认证、超时、取消、重试及错误约定。
- 公开接口：具体路径与方法或公共函数签名、输入输出、权限、版本和并发要求。
- 模块共享结构：定义者、使用者、语义和不变量、依赖方向，以及与存储或传输表示的转换。

结构与行为约束一起设计，明确状态、一致性、失败结果及演进方式。是否共享同一类型按实际语义和依赖关系决定，不默认让所有层共用一份表示。

当方案依赖特定索引来保证数据约束、支撑关键查询，或索引变更影响已有数据上的写入和部署时，在设计中说明目标约束或查询、复用或变更现有索引的理由，以及性能验证与迁移条件。涉及 PostgreSQL 时，使用 [design-postgres-indices](../design-postgres-indices/SKILL.md) 评估候选索引与验证证据；具体 DDL 由 schema 或迁移文件维护。

精确定义由 DDL、schema、OpenAPI、IDL、文件格式规格或源码所有者维护。设计记录关键结构、关系、约束和决策理由，并引用完整定义，避免复制全量目录或维护两套定义。沿用既有约定的普通细节在相应所有者中表达；影响消费者、既有数据、部署或恢复的选择需在架构设计中解释。

### 独立发布与版本共存

对独立部署的服务与独立分发的客户端，将升级不同步、支持范围内的版本共存作为正常运行约束。CLI、桌面端、移动端尤其如此，Web 也按实际更新与缓存方式判断。服务端部署后，支持范围内的已发布客户端仍应正常工作，方案不能以所有客户端同步升级为成立前提。

依据已确认的支持政策，明确服务端与客户端的版本组合、既有行为保证、新能力的启用条件、版本不匹配时的可观察行为，以及必要的弃用和迁移安排。优先沿用既有协议与演进机制；版本共存不自动要求新增版本字段、协商接口或一套新协议，现有机制无法满足具体支持要求时再引入必要能力。支持范围不明时主动提出具体决策问题，不自行承诺永久兼容，也不默认旧客户端立即退出支持。确需中断旧版本支持时，应明确影响、迁移路径和发布条件，并取得相应确认。

共同契约、任务或 PR 的代码交付、制品发布、服务部署和功能启用分别说明。运行时推广顺序是架构约束，代码验收通过受控实例验证候选版本及受支持的版本组合，不等待线上实际升级。同一源码修订的组合验收不能推导为所有组件同任务、同版本或同时部署。需要同步修改或切换时，说明适用边界、分开运行会破坏的具体约定及最小范围；仓库某项功能的局部发布约束不推广为通用规则。

### 迁移与运行机制

迁移设计说明数据和部署如何进入新约定、验证步骤及失败处理。索引迁移涉及已有大表或持续写入的表时，分别验证目标访问路径和变更的上线条件，说明锁与写入影响、切换顺序与恢复方式。旧数据按确认要求迁移，不默认增加旧数据读取分支或未确认的兼容层；独立分发客户端的协议兼容按上述支持政策设计，不能假设数据库迁移会同时升级已经分发的客户端。

涉及运行入口、异步或后台工作、外部事件、并发边界时，必须按 [可观测性设计要求](references/observability.md) 说明相关机制；不适用时给出理由。涉及模型使用的工具表面时，预算描述与 schema、输出形态、往返次数和 token 成本，提供代表性真实数据测量；尚未测量则记录缺口与验证方法，不把估算当收益结论。

## 独立评审与反馈处理

按设计实际涉及的风险选择独立评审视角，如架构、可维护性、性能或可测试性，不机械要求固定人数。作者不能用自查替代独立评审。评审工具接入、结果合同和失败处理遵循 [评审执行要求](../my-design-review/references/execution.md)。

先核对 finding 是否成立并属于确认范围，再按严重程度处理。修复范围内的 Critical/Major 问题；较小改进和新增能力记录为后续建议，不让设计随评审不断扩大。不成立的 finding 保留简洁理由，需要用户选择的事项保留为待决策。

在仓库允许修改的设计所有者中连贯重写，事实与约定同步到所属材料；已接受且不可变的设计按仓库规定的后续记录或替代流程处理，保留原始决策。实质改变关键设计后，重新审查受影响内容；以最终版本没有未解决的 Critical/Major 为收敛条件，不追求消灭所有小建议。真实决策与理由放在设计或决策所有者中，评审过程、运行记录和处置明细放在评审记录或会话中。

## 交付材料与完成状态

交付用户要求的当前材料。项目要求保存到任务描述、附件或其他所有者时，在请求用户审阅前保存完整材料并读回确认，提供真实可访问的引用。

用户确认当前方案与拆分并要求建立实际交付任务时，使用 [dn-create-delivery-tasks](../dn-create-delivery-tasks/SKILL.md) 按确认清单及仓库必需阶段登记并读回；必要后继的登记只按当前范围与已有授权进行，设计或评审完成不自动授权登记或实施。

报告材料位置、当前范围、实际评审者与模型、被审查的文档版本、关键问题处理结果和待决策事项。同模型的多个角色只能报告为独立或多视角评审；只有实际使用不同模型并取得结果时才称多模型评审。

存在未解决的关键决策、Critical/Major 或影响方案成立的重要验证缺口时，报告草案或待决策状态，不能称为可实施或已完成。评审后的提案与用户接受的设计分别表达，用户接受只按实际确认判断。

已有授权要求 PR、Issue 或其他外部交付时，按项目流程完成相应交付，检查实际创建结果并返回引用；仓库要求原生 Issue 或其他登记时，按已有范围与授权创建或复用并核验关联，不额外创建无关工作项。交付失败或只完成一部分时准确说明当前结果，不能用本地文件或推送地址代替尚未创建的外部成果。代码实现由相应的已授权开发流程承担。
