# PR 评论要求

用户实际指定远端 PR 作为审查对象时，默认在该 PR 发布已核实的 inline comments，不重复请求发布确认。用户明确要求只回传报告、不发布或私下审查时遵循该限制；仅将 PR 作为背景或参考资料，不构成对它进行审查和发布的授权。

多代理审查先汇总去重，由负责对外交付的一方统一发布；只读审查子任务不自行写入远端。本地报告和应用内标注不等于远端评论。

发布前重新核对当前 PR、被审提交及 finding，确认问题仍成立。使用准确的 commit、文件路径、diff side 和行号；能对应代码行的 finding 落在相关变更行，不堆成一条顶层评论，也不为了满足接口而挂到无关行。推送可能发生在核对之后，遇到过期坐标或版本变化时重新判断，不能静默归到另一提交。

按目标仓库的评审格式、PR 关联与实际授权发布，在规定允许的位置表明真实 agent 身份；仓库有严格首行或正式结论格式时遵循该要求。每项保留简短、直接的结论、影响和必要修改，不贴调查过程、复现日志、证据清单或方法叙述。这些支持材料放在给用户的报告中。

合并相同根因，避免重复评论。未成立的怀疑、无关清理和纯偏好不发布为缺陷；较小后续项按项目范围规则处置。没有成立的 finding 时不凑出问题；仓库明确要求正式审查结论或完成记录时，按其格式发布真实结果，否则只向用户报告，不发布空评论。发布许可不扩展为代码修改、批准或合并，正式 review 状态遵循实际授权和完整审查结论。

保留提交返回的 review/comment ID，核对实际可见的发布结果；草稿或 pending review 不算已经发布。响应丢失或超时先按原 PR、提交、位置和内容核对，不盲目重复提交。

已授权发布发生可恢复失败时，先核对实际写入状态和当前坐标，在既有权限与重试约定内处理原因，只补交已经确认缺失的评论，再核对结果。写入仍不确定、缺少发布权限或 finding 确实无法对应有效位置时，说明具体缺口与最小所需条件，明确哪些尚未发布，不把本地草稿称为已发布，也不使用无关行或顶部汇总掩盖 inline 发布缺口。
