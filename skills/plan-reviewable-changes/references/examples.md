# 能力与启用的拆分

以下是寻找边界的方法，不是固定阶段数或“一层一个 Task”的模板。是否合并相邻小能力，仍由各单元的实际代码和审查负担决定。

## 配置归属迁移

可以先完成有实际用途的中立错误或解析能力，再按少量相关配置组迁移最终所有者。每组同步自己的字段、受影响调用者和规则测试；尚未迁移部分保持原实现，已经迁移部分直接使用最终定义，不增加叶字段副本或旧/新投影桥接。

最终“所有定义都归所属模块”是整体迁移结果。若要求每一步已经达到全量最终结构，先说明这项约束的必要性；不能仅因多人会改同一聚合文件或需要多跑门禁，就跳过中间粒度。

## 新日志能力

可以分别完成：

- 日志后端及真实文件、锁、轮转和错误状态验证；紧密共享资源状态的行为保留一起。
- 运行配置与验收资源准备，例如容器权限、卷和清理，以提交的配置在独立验收实例中验证。
- 命令接入与启用，依赖后端及必要资源定义，由验收者构建并启动候选服务，验证初始化、取消、关闭与退出结果。

启用前必须具备的权限和隔离条件，通过代码、配置和可获得的验收资源保证。这些前置不要求生产环境先应用配置。后端未接入期间，当前运行路径继续正确；不能先启用再让后续任务补救失败。

## 多消费者采用

已确认旧输入或入口在迁移期间仍然有效时，CLI、Web、部署配置或测试运行器可以按各自上下文完成代码接入。服务已提供新能力而部分用户仍使用旧 CLI，是需要按支持政策覆盖的正常组合。每项代码接入包含自己的验证与文档；组合验收由验收者在受控环境中运行候选服务和指定客户端版本，检查真实交互与持久化读回，不等待线上部署或用户安装。

例如，可先在保持支持范围内旧命令行为的前提下提供服务端新能力，再分别接入 CLI 与 Web，按设计控制新能力的可用条件，并验证支持的新旧版本组合。服务端先行不能仅凭“新增字段”就判为兼容，仍需核对已发布客户端的真实解析与行为约定。

公共约定变化若会破坏仍受支持的消费者，先解决协议演进与迁移设计。仓库要求的最小同步代码修改不代表用户端已同步安装；独立分发客户端的支持变更仍须有明确安排。具备集中切换条件时，可以保留有具体依据的最小共同修改，不为了拆分虚构兼容要求，也不因为同属一个目标就把所有消费者都合并。
