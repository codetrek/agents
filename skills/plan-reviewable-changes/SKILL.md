# 拆解为可独立审查的任务

在编码和并行实施前，先按目标仓库要求确定完整交付流程，再规划其中完整、聚焦、容易审查的改动单元，控制整项工作的交付成本。工作流阶段说明成果与完成条件，代码及文档改动单元说明相应 PR 的审查和交付范围。

## 提前确定交付单元

读取目标仓库适用的开发流程、PR 规范、材料生命周期和已有例外；这些明确要求优先于通用拆分建议，同时遵守指示优先级与已有授权。根据已确认目标识别受影响模块、共同契约、数据变化和验证需求，复用已接受且覆盖当前范围的成果，再沿安全边界分批交付。

仓库要求独立承接、交付或验收且具有明确成果、责任和完成条件的阶段，纳入拆分；使用 Daynight 时可按授权登记为独立 Task。设计材料必须预先合入、独立验收等要求应有真实承接，不能都当作代码实施的内部步骤。文档、commit、命令或一次工具调用本身不构成拆分依据。

用简短清单说明各单元的目标、成果、预计改动范围、候选版本、验证方式与环境、执行责任、前置关系和交付顺序。规模合适的代码改动保持一个单元，仓库要求的独立阶段另行承接；规划不扩大既有授权范围，也不强制新增流程或记录文件。

Task、改动单元、原生 Issue 和 PR 不机械一一对应。按仓库关联规则明确每项范围、成果和完成条件；一个 Task 可交付零个、一个或多个 PR，多项工作共用 PR 证据时，各自完成条件仍须独立成立。

规模预测落实到各单元：按生产、测试、配置或脚本列主要路径与预计文件数（可给区间），说明涉及的职责模块和变化约定，并估算人工改动量或实质审查时间，时间使用分钟。估算标明不确定性，小改动一行即可。

## 每个单元完整且主线安全

完整性针对该单元声明的目标，可以是模块能力、跨模块功能切片、缺陷修复或有独立价值的结构调整，不要求交付整个大型 feature。独立完整可以有明确前置：前置成立后能完成并验证自身目标即可，不要求实现所有前置能力；说明本次结果及留给后续的工作。

包含该改动单元目标所需的调用者调整、测试和适用文档。文档位置、所有者、生命周期及与代码共同或分阶段交付的要求遵循目标仓库；规定预先合入的材料作为后续真实输入。按约定顺序合入后，主线应保持可构建、可测试、可运行，既有行为与数据约定正确；不能依赖后续改动修复当前破坏或补齐必要验证。最终结构可以分批达到，空接口或占位行为不构成完整能力。

## 代码验收的对象与环境

代码验收针对明确提交的 commit 或由其构建的制品，证据绑定实际运行的版本和配置；多个组件列明各自版本。线上实例可能运行不同代码，不能用其状态、Release 记录或现网测试代替候选版本验收。

规划各单元验证和整体端到端验收时，使用 [plan-actionable-verification](../plan-actionable-verification/SKILL.md) 核对指定执行者、环境能力、输入与前置责任，并写出可执行步骤和证据。需要端到端验收时，在可控制的环境运行指定版本的真实客户端、服务端与必要持久化依赖，从公开入口验证主流程、状态变化和读回。

代码验收不以制品发布、线上部署或用户安装升级为隐含前置。运行时升级顺序与功能启用条件仍须设计，并在受控环境验证必要版本组合。实际发布、部署或生产观察仅在明确的运维交付范围中另行承接，不能反过来阻塞已满足自身条件的代码任务。无法准备必要验收环境时，明确缺失输入及责任，继续完成授权内可行的准备；不能通过改看线上、只做静态检查或省略必要 E2E 来宣称验收通过。

## 一个单元只做一件范围适当的事情

所有改动服务于同一个明确目的，避免混入无关功能、重构或清理。

大型 feature 按可独立理解和验证的模块能力、子功能或功能切片拆分。规模合适的完整 feature 可以作为一个单元；一个模块内的多个独立目的也应拆开。模块和目录是可选边界，不是必须采用的切割方式。

目的相同或验收完整不自动证明规模合适。涉及多个可独立验证的机制、广泛消费者或明显不同的验证环境时，先尝试更小、主线安全的完整能力边界。

## 控制代码规模和模块跨度

控制单次修改的生产代码和测试代码文件数，结合改动量、逻辑复杂度和所需背景评估审查负担。文档单列，不计入代码文件数，但仍需审查。

文件过多或理解成本过高时，重新评估拆分，不机械套用统一数量上限。机械批量修改和可复现的生成结果可以保留较大范围，但应说明共同目的、生成方式和验证方法。保留较大组合前，说明尝试过的更小拆法、不能采用的具体原因和预计审查范围，不能只比较一个大改动与极碎的切割。

改动跨越不同客户端、服务或 package 时，优先沿这些边界拆分为独立任务，分别明确成果、验证和完成条件，通过清楚的契约与前置依赖衔接。同属一个 feature 或需要最终端到端验收，不足以将各端的实现合并为一个任务。

确需跨边界共同修改时，说明分开交付会破坏的协议、调用关系、原子性或一致性约定，或拆分后缺乏独立意义的原因，保留最小必要组合。普通调用或实施依赖可以通过前置关系表达，“必须先完成”不等于“必须同次交付”。每个中间状态仍须正确，并明确整体集成与验收的承接。

可独立发布的服务与客户端，按架构中明确的版本共存和支持政策说明运行时升级顺序、新能力启用与消费者采用，不能把用户同步升级作为拆分成立的前提。候选代码与支持版本的组合按上述验收环境规则验证；共享契约或同源码组合验收不自动要求同一 PR、同版本发布或同时部署。代码交付边界、验收证据与实际运行推广分别判断。

以合理的目标架构为依据，优先沿可复用能力、契约与自然交付顺序拆分，必要重构按安全边界纳入当前范围，避免为了少改代码固守不合适的结构。新增机制或协议须有实际需求依据，按 [简单方案与复用要求](../my-architect-and-design/SKILL.md#优先采用简单可行方案) 判断必要性，不能为拆任务反过来制造复杂架构。拆分不应仅为缩小 PR 添加未确认的兼容层、双写、开关或临时适配；正常独立升级所必需的协议兼容按已确认支持政策保留，不能据此要求所有客户端同步替换。相关架构约束见 [独立发布与版本共存](../my-architect-and-design/SKILL.md#独立发布与版本共存)，具体边界示例见 [能力与启用的拆分](references/examples.md)。

共享热点、并发修改和分支存续时间用于安排实施顺序与协作；交付边界仍按完整性、审查负担和验证成本确定。整体设计可以涉及多个模块，实施时控制同时修改的范围。

## 避免过度拆分

拆分应带来更清楚的目的、更低的审查负担或更独立的交付能力，同时考虑重复 CI、Review、上下文切换和依赖维护的成本。这些开销用于比较合理粒度，不能单独豁免明显过大的单元。

在已有单元规模合理的前提下，继续拆分会割裂必须共同理解或验证的改动，产生无独立意义的碎片，或主要增加流程开销时，应保留合理范围内的完整单元。整体目标的验收所有者不要求承担全部消费者的采用修改。

完成拆分前，逐项核对已确认的整体目标、仓库必需阶段、必要集成、消费者代码接入和整体代码验收都有具体单元承接。明确要求的实际运行推广另列成果与责任，不从代码验收自动推导。范围内留给后续的工作明确归属与前置，不能只列为待后续处理；仅规划局部阶段时，明确与其余目标的交接及覆盖边界。该核对不授权登记或执行新任务。

有依赖的单元明确前置关系、当前增量和安全合入顺序。实施或评审补入重要机制、扩大代码范围或增加消费者时，即使目的未变，也重新核对规模预测与更小安全拆法。调整遵循已有授权与项目流程，保留活跃工作的责任和状态，保持每一步主线正确。
