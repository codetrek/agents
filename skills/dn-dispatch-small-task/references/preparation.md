# 任务准备要求

## 项目与已有工作

优先使用用户给出的项目或任务引用；否则核对目标仓库的实际 remote 和项目关联。使用当前 CLI 的项目选择机制，或 MCP 的项目解析能力，不假定存在某个固定 CLI 命令。没有唯一匹配时明确缺失或歧义；查不到项目不代表授权注册项目。

查找相同问题和范围的未完成及已完成工作，再读取候选资源的实际类型、完整描述、来源、依赖和验收。列表、搜索摘要和标题不足以判断复用，附件需单独读取。普通执行任务与 Goal 等上层资源按各自流程处理。

相同工作已完成且没有新的剩余问题时无需再次派发。完成后出现的新问题或新要求，另建独立 Task，或匹配已有的未完成后续任务，不能给已完成任务追加范围、重新派活或自动重开。活跃任务不接管、不重新分配，也不另建替代项来绕过现有执行。中断后先核对已有资源和返回 ID，再恢复未完成操作。

## 内容与材料

内容充分与粒度合适分别核对。按主 skill 引用的拆分规则，确认本任务的能力边界、预计生产与测试代码范围、涉及职责及前置；较大组合需给出更小安全候选和不能采用的原因。完整设计、同一 feature 或全套验收不能替代规模判断。已有任务过大时报告具体缺口，按授权调整方案，不自动重分活跃工作。

独立实现者应能从任务和可读引用中理解问题、选定方案、必要详细设计、实施步骤与验收，无需另行调查来建立根因、选择修复或补齐重大约定。未经验证的 patch 猜测不能写成必需方案。

设计和步骤包含实际需要的组件目标、数据或接口、控制流程、错误、集成及迁移安排。共用细节可以引用明确的所有者，任务自身仍应说明具体贡献和工作边界。前端原型、设计评审或其他前置材料按目标项目要求准备，并验证实际可用性。

任务描述与附件保存有效需求、方案、设计、实施步骤、验收和正式结果。工具安排、会话日程、工作目录、调试经过和操作授权留在会话；不把这些内容包装成任务定义。

来源标明资源身份、实际路径、适用内容及用途，仓库输入使用已核对的不可变版本。不能让 Worker 依赖私有机器路径、临时文件或“看之前聊天”。附件先上传并读回，再写实际引用；保留资源之间的有效相对路径，不重复完整材料。

仅登记真正必要的直接前置关系，并核对其分类与实际图。未完成前置不必自动阻止派发，但选定方案、交换约定和集成步骤必须已经完整定义。未来产物标明其生产任务，不能冒充已有输入；未决前置设计仍是内容缺口。

## 注册与读取

按当前产品手册确定创建状态和参数；创建、允许执行与开始执行是不同操作。当前 CLI 创建默认 `proposed`，已确认工作显式使用 `--status todo`，新任务自动执行关闭。不要假定创建响应支持 `--json`。

保留实际返回的资源 ID，完整读回任务和必要附件，核对目标、方案、步骤、来源、平台、依赖与验收。描述更新写成连贯整体。材料不完整时，对尚未开始、许可关闭且既有准备授权覆盖的任务，补齐可由确认要求与证据确定的内容并重新读回；确需用户决定的，提出具体问题、可选处理、影响与建议，等待答复期间继续不依赖该决定的准备。新任务及原本许可关闭的任务在材料完整前保持关闭；许可已开启或已有执行的任务只读核对。如实报告剩余缺口，不宣称已可派发。

所有写入按当前产品的版本与结果规则执行。创建结果不确定时结合原操作上下文、完整字段和资源身份核对；不能仅凭相同标题或一次空查询判断成功、失败或重新创建。
