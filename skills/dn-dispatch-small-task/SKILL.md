# 派发 Daynight 小任务

准备一个完整、可验证的小改动，并交给已有 Daynight Worker 流程。完成任务准备、权限写入和读回核对后返回，Worker 负责后续实现与交付。

## 确定范围与操作

读取目标项目的指示，沿用当前请求和已有授权。讨论、任务注册、自动派发与本会话执行分别判断；创建或读取这个 skill 不授权操作任务。明确要求自动派发且输入充分时，连续完成准备、注册、核对和派发，不重复请求已有授权。

使用当前可用的 Daynight CLI 或 MCP 工具，按实际手册与 schema 操作。CLI 可用时读取 `daynight --version`、`daynight --skill` 和相关命令的 `--help`。服务、身份或工具不可用时如实说明，继续可独立完成的已授权准备。

小任务应交付较小、可独立验证的具体能力，可以有明确前置；一个目的或完整验收不足以证明规模合适。按 [plan-reviewable-changes](../plan-reviewable-changes/SKILL.md) 核对代码范围、职责、预测与更小安全边界，不仅凭字数或文件数判断。先核对相关代码、需求和调用者，区分现象与猜测；必要的需求、根因、方案、接口、迁移或架构决策在派发前解决，多阶段目标遵循项目的 Goal 流程。

## 准备可实施的任务

按 [准备要求](references/preparation.md) 选择项目、查重和读取完整候选任务。已有相同标题不等于相同工作，活跃任务的范围和责任必须保留。

标题描述结果，内容让没有原会话的实现者能够独立实施：

| 内容 | 要求 |
|---|---|
| 问题与目的 | 触发条件、实际现象、期望行为、消费者和影响 |
| 范围 | 独立交付的结果、涉及的边界及必须保持的行为 |
| 方案与设计 | 选定机制、必要理由、组件与数据或接口、错误及集成要求 |
| 实施步骤 | 有顺序的修改目标、预期结果和必要依赖关系 |
| 来源 | 实际可读的需求、代码和材料，明确用途与已验证的不可变版本 |
| 验收与交付 | 成功、失败和重要回归行为，验证方式、适用检查及完成条件 |

不能把确认问题、选择方案或补齐设计留成 Worker 的隐含任务。正常代码阅读、局部编码选择、实现调试和验证仍由 Worker 完成，不要求逐行代码指令或空模板。

## 选择平台

按真正需要的实施与验证环境设置 `requiredPlatform`：

| 值 | 含义 |
|---|---|
| `null` | 不要求特定操作系统 |
| `windows` | 需要原生 Windows |
| `linux` | 需要原生 Linux；WSL 的 Linux runtime 属于此项 |
| `macos` | 需要原生 macOS |

限制平台时说明依据，不按当前主机、报告提到的系统、模型或 Worker 身份选择。多系统验证明确如何取得全部证据，可使用适用的已有 CI；单个字段不能表达系统集合，执行环境无法满足时先调整验证安排或任务边界。

## 注册、派发与返回

为已确认且明确要求自动派发的新任务显式选择 `todo`，新任务先保持 `allowAgents=false`。仅注册的请求保留选定创建状态，默认 `proposed`，在注册并完整读回后结束。已有 `proposed` 沿用状态与权限，只有当前请求或已有授权明确选择 `todo` 时才转换。

先保存并读回完整任务和真正需要的材料，核对平台与依赖。使用 [dn-handoff](../dn-handoff/SKILL.md) 对该 Task 核对内容、独立认证的责任身份和状态；通过后用最终审阅的准确版本启用许可，并核对响应及最终资源。

返回任务引用、内容与责任核对结论、实际修改或缺口，以及观察到的版本、负责人、平台、权限、状态、依赖阻碍和 Worker 归属。区分确认写入、结果不确定和只读核对。

`allowAgents=true` 表示执行许可，不证明 Worker 已启动或任务已交付。完成核对后返回，不等待 claim、不启动本地实现、不选择更多任务。
